# L39 实践：动手集合通信，从原语语义到 α-β 曲线

> [!abstract] 本课速览
> 这一课不再画棋盘，而是让 8 个本地进程真的交换 tensor。完成实验后，你将能够：
> 1. 用 **torchrun**（PyTorch 分布式进程启动器）启动 8 个 ranks，并逐项核对 broadcast、all-gather、reduce-scatter、all-reduce、all-to-all 的输入输出；
> 2. 亲手验证 $	ext{all-reduce}=	ext{reduce-scatter}+	ext{all-gather}$；
> 3. 从 1 KB 扫到 64 MB，画出时间—消息大小的 log-log 曲线；
> 4. 拟合 whole-collective 的有效 $hat\alpha_{op}$ 与 $hat\beta_{op}$，并解释它们为什么不等于一跳链路参数；
> 5. 读懂一份可追溯的 8×H100 `nccl-tests` 实测片段，并用 5 ms **straggler**（掉队者 / 慢 rank）亲眼看到木桶效应。
>
> 前置：[[L38 NCCL解剖]] · 预计 60–90 分钟

## 本次实践你要亲眼看到什么

1. 8 个 ranks 分别拿着 `tensor([0])` 到 `tensor([7])` 做 all-reduce，最后每个 rank 都得到 $0+1+\cdots+7=28$。
2. 同一份向量先做 reduce-scatter、再做 all-gather，结果与直接 all-reduce **逐元素完全一致**。
3. 小消息从 1 KB 逐步增大时，时间先近似不变；到大消息区后，时间随字节数近似线性增长。
4. 脚本打印本机的有效 $\hat\alpha_{op}$、$\hat\beta_{op}$、交叉点与有效带宽，并生成 CSV 和 log-log SVG。
5. 某个 rank 在 all-reduce 前 `sleep(5 ms)` 时，其他 ranks 即使准时到达也要一起等它。

前四课把 collective 讲成了“谁给谁什么数据”和“需要多少步”。这一课把棋盘上的箭头换成进程、socket、tensor 和墙钟。以后看到训练作业卡在 all-reduce，你至少能先问：是语义没对齐、固定开销太高、带宽没跑满，还是有 rank 掉队？

## 〇、环境准备

### 0.1 一台普通笔记本就够

最低硬件是一台能同时运行 8 个 Python 进程的 CPU 笔记本。Apple Silicon 也可以，但这里的 **Gloo**（CPU 通信后端）使用 CPU tensor，==不是把 tensor 放到 MPS 上==。8 ranks 扫到 64 MB 时，仅用户 buffer 合计就至少是

$$
8\times64\ \text{MB}=512\ \text{MB},
$$

还没算 Python、PyTorch 和通信库的内部空间。如果机器内存紧张，先用 `--nproc_per_node=4 --max-bytes 16000000` 跑通流程，再做完整实验。

本课代码按 Python 3.9–3.12、`torch==2.5.1` 实测；`numpy` 不是脚本计算所需依赖，但安装后可避免 PyTorch 的可选依赖提示。单位沿用 [[03 约定与符号]]：1 KB = 1,000 B，1 MB = 1,000,000 B。

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install "torch==2.5.1" "numpy==1.26.4"
```

完整单文件在 [[L39_collectives.py]]。它只依赖 `torch` 与 Python 标准库，CSV、拟合和 SVG 绘图都在同一文件中完成，不需要 Jupyter、NumPy 或 Matplotlib。

### 0.2 先确认启动链路

`torchrun` 为每个子进程设置 `RANK`、`WORLD_SIZE`、`LOCAL_RANK`、rendezvous 地址等环境变量。每个进程运行同一份程序，再用自己的 **rank**（进程编号）走不同数据分支；这就是 [[L36 集合通信原语|SPMD]] 的实际样子。`--standalone` 会在本机建立单节点 rendezvous：

```bash
torchrun --standalone --nproc_per_node=8 \
  "M5 集合通信/实践代码/L39_collectives.py" \
  --backend gloo --task semantics
```

正常启动时，第一行应包含：

```text
torch=2.5.1 backend=gloo device=cpu world_size=8
```

若端口或旧进程残留导致 rendezvous 失败，先确认上一条 `torchrun` 已退出，再重试；不要让两组实验共用一组 ranks。脚本把 process group timeout 设为 5 分钟，某个子进程提前报错时，应先找所有 ranks 中时间最早的 traceback，不要只盯着最后一个超时者。这正是 [[L38 NCCL解剖]] 的排障习惯。

### 0.3 有 8 张 NVIDIA GPU 时切到 NCCL

每个进程必须独占一张 GPU。脚本会按 `LOCAL_RANK` 绑定设备：

```bash
torchrun --standalone --nproc_per_node=8 \
  "M5 集合通信/实践代码/L39_collectives.py" \
  --backend nccl --task all
```

不要拿笔记本 Gloo 的时间和 8×H100 NCCL 直接排名。前者主要练 API、语义和测量方法；后者才会经过 CUDA、NVLink/NVSwitch 与 NCCL 的算法—protocol 选择。

## 一、逐步任务

### 任务 A：五种原语到底把什么送到了哪里

脚本先让 rank $r$ 构造 `tensor([r])`。但 reduce-scatter 与 all-to-all 不能只拿一个标量：它们需要为多个输出 ranks 准备分片。因此脚本在这两步把输入扩展为

$$
x_r=[8r,8r+1,\ldots,8r+7].
$$

运行 Task A 后，对照下表检查。不要只看 `[PASS]`；先用 [[L36 集合通信原语]] 的棋盘语义自己预测一遍。

| 原语 | rank $r$ 的输入 | rank $j$ 的预期输出 | $p=8$ 的例子 |
|---|---|---|---|
| broadcast | `[r]` | root rank 0 的 `[0]` | 所有 ranks 都是 `[0]` |
| all-gather | `[r]` | 按 rank 顺序拼接所有输入 | `[0,1,2,3,4,5,6,7]` |
| reduce-scatter | `[8r,...,8r+7]` | 第 $j$ 个规约结果 | $224+8j$ |
| all-reduce | `[r]` | 所有标量之和 | `[28]` |
| all-to-all | 第 $d$ 个元素发给 destination $d$ | 收到每个 source 给自己的元素 | rank $j$ 得到 `[j,8+j,...,56+j]` |

reduce-scatter 的 $224+8j$ 不是魔法。rank $j$ 收到每个 source 的第 $j$ 个元素，所以

$$
\sum_{r=0}^{7}(8r+j)
=8\sum_{r=0}^{7}r+8j
=8\times28+8j
=224+8j.
$$

于是 rank 0 得到 224，rank 3 得到 248，rank 7 得到 280。一次实测输出的首尾两行是：

```text
rank=0 ... reduce_scatter=[224.0] all_reduce=[28.0]
  all_to_all=[0.0, 8.0, 16.0, 24.0, 32.0, 40.0, 48.0, 56.0]
rank=7 ... reduce_scatter=[280.0] all_reduce=[28.0]
  all_to_all=[7.0, 15.0, 23.0, 31.0, 39.0, 47.0, 55.0, 63.0]
```

#### 一个不能藏起来的 backend 边界

**torch.distributed**（PyTorch 分布式通信包）提供统一 API，但不表示每个 backend 都实现了每个 API。PyTorch 官方 backend 能力表把 Gloo 的 CPU all-to-all 标为不支持；脚本因此在 NCCL 路径调用原生 `all_to_all_single`，在 Gloo 路径明确打印：

```text
fallback all_gather + local column select
```

它先 all-gather 出 `gathered[source, destination]` 矩阵，再让 rank $j$ 取第 $j$ 列。输出语义与等长 all-to-all 相同，但通信量、算法与性能都不同，==只能用来验语义，不能拿它测 Gloo 原生 all-to-all 性能==。reduce-scatter 则优先调用 `reduce_scatter_tensor`；若某个旧构建拒绝该 API，脚本才退化为 all-reduce 后本地切片，并同样把后备路径打印出来。官方支持边界应以你安装版本的 [PyTorch distributed 文档](https://docs.pytorch.org/docs/stable/distributed.html) 为准。

> [!warning] “API 名一样”不等于“backend 能力一样”
> 写论文复现实验时，至少记录 PyTorch 版本、backend、device、world size 与后备路径。否则“我跑了 all-to-all”可能其实只说明输出 shape 对了，并不能说明你测到了目标通信算法。

### 任务 B：自己拼出 all-reduce

[[L37 通信算法与代价模型]] 已经推导过 ring all-reduce 的两阶段结构。现在把等式真的跑一遍：

$$
\operatorname{AllReduce}(x)
=\operatorname{AllGather}(\operatorname{ReduceScatter}(x)).
$$

```bash
torchrun --standalone --nproc_per_node=8 \
  "M5 集合通信/实践代码/L39_collectives.py" \
  --backend gloo --task duality
```

每个 rank 构造一个 32 元素向量，直接 all-reduce 得到 `reference`；另一条路径先拿到自己负责的 4 元素规约分片，再 all-gather 还原 32 元素完整向量。脚本用 `rtol=0, atol=0` 逐元素断言完全相等：

```text
[PASS] Task B: reduce-scatter + all-gather 与 all-reduce 完全一致
  (elements=32, RS=native reduce_scatter_tensor)。
first_values=[2800.0, 2808.0, 2816.0, 2824.0, ...]
```

```mermaid
flowchart LR
    X["每个 rank 的完整贡献向量"] --> AR["all-reduce"] --> FULL1["每个 rank 都有完整规约结果"]
    X --> RS["reduce-scatter"] --> SHARD["每个 rank 只留 1/p 规约分片"]
    SHARD --> AG["all-gather"] --> FULL2["每个 rank 都有完整规约结果"]
    FULL1 -. "逐元素相等" .- FULL2
```

这就是“读懂 ZeRO 的钥匙自己造一遍”：如果下一步计算只需要本 rank 的 shard，就可以停在 reduce-scatter 后，不必立即复制完整结果；需要完整量时再 all-gather。[[L42 ZeRO与FSDP]] 会把这个等式用于参数、梯度和优化器状态的切分。

### 任务 C：从 1 KB 扫到 64 MB，拟合有效 α 和 β

运行完整扫描：

```bash
torchrun --standalone --nproc_per_node=8 \
  "M5 集合通信/实践代码/L39_collectives.py" \
  --backend gloo --task benchmark
```

脚本的测量纪律比“循环外套两个时间戳”多几步：

1. 每个消息大小先 warm up 3 次，避免把首次初始化全塞进样本；
2. 用 barrier 让所有 ranks 从同一轮测量起跑；
3. 小消息最多重复 50 次，大消息至少重复 5 次，取每次平均；
4. 以所有 ranks 的最大完成时间代表同步作业时间，因为训练 step 要等最慢 rank；
5. payload 使用全 0 tensor，使重复 SUM 不会数值爆炸，也不把重新填充 buffer 的时间算进 collective；
6. rank 0 写出 `outputs/l39/all_reduce.csv` 与 `outputs/l39/all_reduce_loglog.svg`。

我们对整次 all-reduce 写一个操作级模型：

$$
T_{op}(n)\approx\hat\alpha_{op}+n\hat\beta_{op}.
$$

脚本以 16 KB 及以下点的时间中位数估计小消息平台 $\hat\alpha_{op}$，以 4 MB 及以上点对 $T=a+n\hat\beta_{op}$ 做最小二乘拟合，再报告

$$
B_{eff}=\frac{1}{\hat\beta_{op}},\qquad
n^*=\frac{\hat\alpha_{op}}{\hat\beta_{op}}.
$$

这里特意加了下标 `op`。[[L37 通信算法与代价模型]] 里的 $\alpha$ 常指每一步/每消息的底层固定代价；本实验拟合的是完整 collective 的有效截距，包含 Python 调用、process group、进程调度、同步、Gloo transport 和算法步数。它可以比较同机同配置的实验，却不能直接冒充 RDMA 一跳时延。

> [!example] 算一算：本次实现自测的两段式曲线
> 2026-08-05 在一台 Apple arm64 笔记本上，以 `torch==2.5.1`、8 个 Gloo ranks 运行上述命令，得到一次实现自测：
>
> $$
> \hat\alpha_{op}=3.7606\ \text{ms},\qquad
> \hat\beta_{op}=1.430162\ \text{ns/B}.
> $$
>
> 有效大消息带宽为
>
> $$
> B_{eff}=\frac{1}{1.430162\times10^{-9}}
> \approx0.699\times10^9\ \text{B/s}
> =0.699\ \text{GB/s}.
> $$
>
> 固定项与带宽项相等的交叉点为
>
> $$
> n^*=\frac{3.7606\times10^{-3}}{1.430162\times10^{-9}}
> \approx2.629\times10^6\ \text{B}
> =2.629\ \text{MB}.
> $$
>
> 用两项模型预测 64 MB：
>
> $$
> T(64\ \text{MB})
> \approx3.7606\ \text{ms}
> +(64\times10^6)(1.430162\ \text{ns/B})
> \approx95.29\ \text{ms}.
> $$
>
> 同一次扫描实测为约 93.36 ms，数量级与斜率吻合。小消息从 1 KB 增到 16 KB，消息放大 $16\times$，时间仍约 3.74–3.79 ms；这就是平台。64 MB 的 $n/T\approx0.685$ GB/s 已接近拟合渐近值；这就是斜线。

同一次运行中，rank 0 单独做 64 MB 本地 `copy_`，按一份 payload 计约 50.8 GB/s。它远高于 8-rank all-reduce 的约 0.7 GB/s，说明这个实验不是单纯被 `memcpy` 上限卡住：多进程协调、Gloo transport、同步与多步数据运动都在路径上。两者也不是严格 apples-to-apples——copy 实际有读和写，而 `n/T` 只按一份用户 payload 记账——所以正确结论是“通信路径还有大量额外工作”，不是“内存利用率恰好等于 $0.7/50.8$”。

> [!tip] 先看形状，再看绝对值
> 不同笔记本的毫秒和 GB/s 会差很多。你首先要找的是“小消息近似平台、大消息近似直线”，然后再固定版本、进程数、消息范围与计时口径比较绝对值。

### 任务 D：读一份真实的 8×H100 `nccl-tests` 输出

下面不是构造教学数据。它摘录自 NVIDIA `nccl-tests` 官方仓库公开 issue 的一张单节点 8×H100 80GB HBM3 实测截图，命令为 `all_reduce_perf -b 8 -e 256M -f 2 -g 8`；原始截图与讨论见 [NVIDIA/nccl-tests issue #212](https://github.com/NVIDIA/nccl-tests/issues/212)。表中只抄 out-of-place 的代表行，未出现的环境信息不自行补造。

| `size (B)` | `time (µs)` | `algbw (GB/s)` | `busbw (GB/s)` | `#wrong` |
|---:|---:|---:|---:|---:|
| 8 | 32.27 | 0.00 | 0.00 | 0 |
| 1,024 | 33.67 | 0.03 | 0.05 | 0 |
| 16,384 | 34.35 | 0.48 | 0.83 | 0 |
| 1,048,576 | 67.40 | 15.56 | 27.23 | 0 |
| 16,777,216 | 115.6 | 145.08 | 253.89 | 0 |
| 67,108,864 | 315.6 | 212.65 | 372.14 | 0 |
| 268,435,456 | 1,094.6 | 245.23 | 429.15 | 0 |

按 [[L38 NCCL解剖]] 的顺序读：

1. **先看正确性**：每一行 `#wrong=0`，输出校验没有发现错误。高带宽但 `#wrong>0` 的结果不能用。
2. **再看小消息平台**：8 B 到 16,384 B 放大 $2,048\times$，时间只从 32.27 µs 变为 34.35 µs，约 $1.064\times$。这段主要由固定开销决定。
3. **最后看大消息**：64 MiB 到 256 MiB 时，时间随 size 明显增加，algbw/busbw 向上爬升；最后一行仍不能单独证明已到稳定平台。
4. **复算 busbw**：$p=8$ 的普通 P2P all-reduce 折算系数为 $2(p-1)/p=14/8=1.75$，所以

$$
245.23\times1.75=429.1525\ \text{GB/s},
$$

与表中 429.15 GB/s 一致。

[[03 约定与符号]] 给 H100 SXM 的 NVLink 双向合计约 900 GB/s，即每方向约 450 GB/s。若只做 P2P-equivalent 参照，最后一行是

$$
429.15/450\approx95.4\%.
$$

但不要马上写“NVLink 物理利用率 95.4%”。该 issue 中 NVIDIA 维护者明确解释：H100 上的 NVLink SHARP / NVLS 会改变 all-reduce 的数据运动，`nccl-tests` 又不知道 NCCL 内部选了什么算法；此时 busbw 更像“达到同样性能所需的 P2P 等效带宽”，不一定对应线上真实字节率。再加上截图没有完整列出 NCCL/CUDA/driver 版本、算法、protocol 与拓扑日志，最稳妥的体检结论是：==正确性通过，小消息平台清楚，大消息性能持续爬升；要判断是否健康，还需更大消息、完整环境记录和 NCCL 日志。==

## 二、观察与解释：把输出接回 L36–L38

| 你亲眼看到的现象 | 接回哪一课 | 应该如何解释 |
|---|---|---|
| 8 个 `[rank]` 经 all-reduce 都变成 `[28]` | [[L36 集合通信原语]] | “规约后复制给全员”不是一句定义，而是每个 rank 都通过断言的 postcondition。 |
| RS+AG 与 AR 逐元素完全相等 | [[L37 通信算法与代价模型]] | all-reduce 可以拆成“先规约并切分、再收集分片”；优化算法改变路线，不改变数学结果。 |
| 小消息时间几乎不随 size 变 | [[L37 通信算法与代价模型]] | $\alpha$ / 软件固定开销占主导，再加几 KB payload 不是主要矛盾。 |
| 大消息时间近似随 size 线性增长 | [[L37 通信算法与代价模型]] | $n\beta$ 开始主导，斜率的倒数给出 whole-collective 有效带宽。 |
| Gloo all-to-all 打印 fallback | [[L38 NCCL解剖]] | framework API、backend 能力和硬件路径是三层；不能只凭函数名推断实现。 |
| `algbw` 与 `busbw` 不同 | [[L38 NCCL解剖]] | 前者是 $n/T$，后者乘原语流量系数；NVLS 下后者更不能直接当 wire rate。 |

## 三、挑战题：给一个 rank 塞进 5 ms 石头

运行：

```bash
torchrun --standalone --nproc_per_node=8 \
  "M5 集合通信/实践代码/L39_collectives.py" \
  --backend gloo --task straggler \
  --straggler-rank 1 --straggler-ms 5 --straggler-iters 10
```

每一轮先 barrier；计时开始后，rank 1 在进入 1 MB all-reduce 前睡 5 ms，其他 ranks 直接进入 collective。脚本仍取所有 ranks 中最大完成时间，并把 10 轮均值与无 sleep baseline 对比。

一次实现自测得到：

```text
[PASS] Challenge: baseline=5.030 ms straggler=10.355 ms
delta=5.325 ms (rank=1 sleep=5.000 ms)
```

额外 5.325 ms 与注入的 5 ms 同量级，多出的零点几毫秒来自调度抖动与测量噪声。关键不是恰好等于 5.000：all-reduce 是全员依赖，七个准时 ranks 无法绕过一个迟到 rank。后续 [[L53 大规模训练可靠性]] 会把这块 5 ms 石头换成慢 GPU、网络拥塞、重传、GC、故障与恢复。

继续挑战：

1. 把 `--straggler-ms` 依次改成 1、2、5、10，画 `sleep` 与 `delta`；若不近似 $y=x$，检查 timer、barrier 和系统负载。
2. 分别用 1 KB、1 MB、64 MB tensor 注入相同 sleep，回答固定 5 ms 在三个消息区间占总时间的比例为什么不同。
3. 有 8 张 NVIDIA GPU 时用 NCCL 重跑 Task A–C，记录 `NCCL_DEBUG=INFO` 下实际算法、protocol 与 channels，再解释曲线拐点。
4. 把 world size 改为 2、4、8，只比较同一机器、同一版本、同一消息范围；观察 $\hat\alpha_{op}$ 是否随参与者增加。

## 回到本次实践

现在逐项回看开头的五个目标：

1. 你已经看到 rank 0–7 的 all-reduce 结果全是 28，也能用棋盘语义预测其他四个原语的输出，而不是只会背 API 名。
2. 你亲手让 reduce-scatter 产出 shards，再用 all-gather 还原完整结果；“AR=RS+AG”已经从公式变成了零容差断言。
3. 你知道怎样从 1 KB 扫到 64 MB：warm up、barrier、重复、取最慢 rank、保存原始 CSV，而不是只挑一个好看的峰值。
4. 你能区分 whole-collective 的 $\hat\alpha_{op},\hat\beta_{op}$ 与底层单步参数，并用交叉点判断平台何时转成斜线。
5. 你能从真实 `nccl-tests` 表中先查 `#wrong`、再看小消息 time、最后复算 algbw/busbw；也亲眼看到一个 5 ms straggler 如何拖慢全组。

## 术语卡片：亲手验证的 6 个结论

| # | 亲手验证的结论 | 一句话证据 |
|---:|---|---|
| 1 | collective 的定义是每个 rank 的输入输出约束 | 8 ranks 的 all-reduce 都从各自 `[rank]` 变为 `[28]`。 |
| 2 | all-reduce 可分解为 reduce-scatter + all-gather | 两条路径对 32 元素向量逐元素零误差一致。 |
| 3 | 小消息首先撞上固定开销平台 | 1–16 KB 放大 16 倍，Gloo 实测时间仍约 3.76 ms。 |
| 4 | 大消息区的时间斜率给出有效 $\beta$ | 4–64 MB 拟合得到本次运行的 $\hat\beta_{op}\approx1.43$ ns/B。 |
| 5 | busbw 是折算指标，不总是线上物理带宽 | 8-rank all-reduce 用 $1.75\times$ algbw 复算；NVLS 下只是 P2P-equivalent。 |
| 6 | 同步 collective 受最慢 rank 支配 | rank 1 睡 5 ms，1 MB all-reduce 平均增加约 5.33 ms。 |

## 自测

1. 8 个 ranks 分别输入 `[0]` 到 `[7]`，SUM all-reduce 后为什么每个 rank 都是 28，而不是只有 rank 0 是 28？
2. Task A 中 rank 3 的 reduce-scatter 输出是多少？写出完整算式。
3. 为什么 Gloo 路径用 all-gather + 本地选列得到正确 all-to-all 输出后，仍不能据此报告“Gloo all-to-all 带宽”？
4. 某次拟合得到 $\hat\alpha_{op}=3.7606$ ms、$\hat\beta_{op}=1.430162$ ns/B。预测 64 MB all-reduce 时间，并求交叉消息大小。
5. 8-rank `nccl-tests` 某行 algbw 为 245.23 GB/s。按普通 P2P all-reduce 口径复算 busbw；为什么 NVLS 下不能把它直接叫做物理 wire rate？
6. baseline 为 5.03 ms，给 rank 1 注入 5 ms sleep 后变为 10.355 ms。慢化了多少？为什么可能不是精确的 5.000 ms？
7. 比较两台机器的 $\hat\alpha_{op}$ 前，至少要固定或记录哪些实验条件？

> [!note]- 参考答案
> 1. all-reduce 的语义是“规约 + 把完整结果交给所有 ranks”，不是只把结果交给 root；$\sum_{r=0}^{7}r=8\times7/2=28$。
> 2. $\sum_{r=0}^{7}(8r+3)=8\times28+8\times3=224+24=248$。
> 3. 该后备实际传输的是完整 all-gather 矩阵，再本地取列；它只保持输入输出语义，字节量、通信调度和算法都不是原生 all-to-all，性能没有可比性。
> 4. $T=3.7606\ \text{ms}+64\times10^6\times1.430162\ \text{ns}\approx95.29$ ms；$n^*=3.7606\times10^{-3}/(1.430162\times10^{-9})\approx2.629$ MB。
> 5. 系数为 $2(8-1)/8=1.75$，所以 busbw $=245.23\times1.75=429.1525$ GB/s。NVLS 让 NVSwitch 参与归约，实际数据路径不再是 busbw 公式假设的普通 P2P 传输；此值是等效折算指标。
> 6. $10.355-5.030=5.325$ ms。进程调度、计时分辨率、barrier 后到达差异和系统背景负载都会引入抖动。
> 7. 至少记录 PyTorch 版本、backend、CPU/GPU 与互联、world size、消息大小范围、warm-up/repeat 次数、计时统计量、进程/线程绑定、后备路径和系统负载；GPU 实验还应记录 CUDA/NCCL/driver、算法与 protocol。
