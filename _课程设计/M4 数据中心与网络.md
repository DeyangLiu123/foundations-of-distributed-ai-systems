# M4 数据中心与网络 · 设计稿

> 模块目标：把「本科计算机网络」升级成「AI 集群网络」。这是课题组的主场模块：SIGCOMM/NSDI 上 AI infra 论文的背景知识全在这里。网络方向的读者可快读 L28，但 L29–L33 对所有人都是新知识。每课都要回答：这个机制如何影响训练/推理 workload。

## L27 走进AI数据中心

- **文件**：`M4 数据中心与网络/L27 走进AI数据中心.md`
- **定位**：物理世界巡礼：从园区到机柜到一台服务器，AI DC 与传统云 DC 的分野。建立「前端网/后端网」「功率密度」两个核心观念。
- **前置**：[[L25 节点内互联]]
- **核心问题**：① 一个万卡集群在物理上长什么样、由什么组成？② AI 数据中心与「放网站的数据中心」差在哪？③ 为什么 2025 年后新闻天天谈「电力不够」？
- **内容要点**：
  1. 空间层级：campus → building → hall → row → **rack**（机柜）→ server；一个 8 卡 H100 节点占多少 U、耗多少电（~10 kW）→ 一柜放不下几台 → AI DC 的**功率密度**问题（传统柜 ~10 kW vs GB200 NVL72 一柜 ~120 kW）。
  2. 供电与散热：PUE 定义与量级（1.1–1.5）；风冷→**液冷**（cold plate）的时代转折；「训练负载的功率波动会冲击电网」一句话（新研究方向提名）。
  3. **多张网**（本课核心观念）：**back-end network**（GPU 间训练/推理流量，IB/RoCE，带宽怪兽）、**front-end network**（用户请求/管理/存储，普通以太网）、storage network、management network（BMC）。一台 GPU 服务器插着 10+ 根线的解剖图。
  4. 规模谱系：千卡（一个 pod）→ 万卡（Llama-3 级，~25 MW）→ 十万卡（xAI Colossus 级，>100 MW）→ 吉瓦级园区（2026 前沿）；「集群规模受限于单楼供电 → 跨楼跨域训练」的伏笔（L63）。
  5. AI DC vs 云 DC 对照表：流量方向（east-west 主导且同步突发）、租户模型（少量大作业 vs 海量小租户）、故障容忍哲学（作业级重来 vs 实例级迁移）、网络设计目标（对分带宽 vs 灵活多租）。
  6. 名词速览：availability zone/region（云语境，L63 用）、colocation、hyperscaler。
- **必收术语**：datacenter、rack、U（机架单位）、pod、power density、PUE、liquid cooling、cold plate、back-end/front-end network、storage network、management network、BMC（认名）、east-west vs north-south traffic、hyperscaler、availability zone/region、colocation、megawatt（作为集群规模单位）。
- **定量环节**：功率账：16384×H100，每卡 700 W + 节点其他开销 → 每节点 ~10 kW × 2048 节点 ≈ 20 MW IT 负载 × PUE 1.2 ≈ **25 MW**（≈ 2.5 万户家庭）；电费：25 MW × 24h × $0.08/kWh ≈ $4.8 万/天。「算力即电力」的体感。
- **图示**：① 数据中心空间层级图；② 一台 GPU 服务器的「插线图」（几张网各插哪）；③ AI DC vs 云 DC 对照表。
- **延伸阅读**：《The Datacenter as a Computer》（Barroso et al.，第 3 版，选读第 1 章——领域圣经）；SemiAnalysis 关于 AI datacenter 的公开文章（体感数字丰富）。
- **误区**：「数据中心网络 = 一张网」——至少四张，论文说 network 时先问是哪张；「云上租卡和自建集群一样」——网络拓扑透明度、亲和性控制完全不同（研究复现的现实约束）。

## L28 数据中心网络基础

- **文件**：`M4 数据中心与网络/L28 数据中心网络基础.md`
- **定位**：桥梁课：把本科网络知识对接到 DC 场景，补齐 Clos/收敛比/对分带宽这套 DC 专属词汇。网络方向读者可快读，但「AI 流量为什么难伺候」一节人人必读。
- **前置**：[[L27 走进AI数据中心]]
- **核心问题**：① 为什么 DC 网络长成 leaf-spine 而不是随便一棵树？② oversubscription、bisection bandwidth 怎么算？③ AI 流量和 Web 流量的统计性格差在哪？
- **内容要点**：
  1. 快速回顾（半页速通，网络背景读者跳过）：分组交换、Ethernet/IP/TCP 分工、RTT、串行化时延 vs 传播时延；单位纪律再强调（Gb/s vs GB/s，回收 03）。
  2. 从树到 **Clos/fat-tree**：单根树的根瓶颈 → 多级多路径；**leaf-spine（2 层）**与 3 层 fat-tree 的构造法（以 64 口交换机为例手搭一个）；**radix** 概念。
  3. 三个核心度量：**oversubscription**（收敛比，下行:上行）、**bisection bandwidth**（对分带宽——最坏切一刀的截面带宽）、full bisection / non-blocking 的含义；为什么云 DC 敢 3:1 收敛而 AI 后端网普遍 1:1（流量模型不同）。
  4. AI 流量画像（本课灵魂，为 L30–L32 立靶）：**少流、大流、同步突发**——集合通信产生的流量在同一瞬间从所有节点爆发（bursty & synchronized）、流数极少（每 GPU 几条大象流）、语义上「最慢的流决定全局」（**straggler 放大效应**——一条慢流拖死一次 all-reduce）。与 Web 流量（海量短流、统计复用友好）对照表。
  5. TCP 在此的困境预览：内核开销、慢启动、突发丢包 → 引出 L29 RDMA；「为什么不能就用 TCP 跑训练」一段话。
- **必收术语**：packet switching、RTT、serialization delay、propagation delay、Clos network、fat-tree、leaf-spine、ToR（top-of-rack）、spine/aggregation/core、radix、oversubscription、bisection bandwidth、full bisection、non-blocking、east-west traffic（回收）、elephant/mice flow、flow completion time（FCT）、incast（预告）、bursty traffic、synchronized traffic。
- **定量环节**：手搭拓扑：64 口 400G 交换机，两层 leaf-spine 无收敛 → 每 leaf 32 下 32 上 → 32 leaf × 32 spine 口 = 最多 1024 端口 = 1024 GPU（每 GPU 一网卡）；对分带宽 = 1024×400G/2 = 204.8 Tb/s。再算 3 层 fat-tree 能扩到多少（k=64: k³/4 = 65536 端口）。「一道题记住拓扑扩展性公式」。
- **图示**：① leaf-spine 与 3 层 fat-tree 结构图（标端口数）；② AI vs Web 流量对照的时序示意图（同步脉冲 vs 泊松噪声）。
- **延伸阅读**：《A Scalable, Commodity Data Center Network Architecture》（SIGCOMM 2008，fat-tree 开山，读前 3 节）；Meta 关于 AI 训练流量特征的公开论文/博客（如 SIGCOMM 2024 RDMA at scale 的 workload 节，预告 L29/L67）。
- **误区**：「带宽大就不会拥塞」——同步突发下瞬时全员打满，拥塞是常态；「对分带宽 = 交换机总带宽」——是最坏切面；「AI 流量 = 大流量的 Web」——统计性格完全不同，机制设计因此不同。

## L29 RDMA原理

- **文件**：`M4 数据中心与网络/L29 RDMA原理.md`
- **定位**：AI 后端网的事实标准传输。讲清 kernel bypass/zero copy 的革命点、verbs 编程模型的名词体系、IB 与 RoCEv2 两大阵营。NSDI/SIGCOMM 论文的 RDMA 术语在此一网打尽。
- **前置**：[[L28 数据中心网络基础]]
- **核心问题**：① RDMA 到底 remote 在哪、direct 在哪？② QP/CQ/verbs 这套黑话怎么对应到「发一次数据」？③ InfiniBand 和 RoCE 怎么选（论文里为什么两派都有）？
- **内容要点**：
  1. TCP 栈的账单：每次收发的内核穿越、内存拷贝、中断、CPU 占用（数字级：跑满 400G 的 TCP 要烧掉多少核）→ 三板斧革命：**kernel bypass**（用户态直通网卡）、**zero copy**（应用缓冲区直达网线）、**CPU offload**（传输逻辑下沉网卡硬件）。
  2. **verbs 模型**（名词地图，配主图）：**QP**（queue pair，SQ+RQ）、**WR/WQE**（work request）、**CQ/CQE**（completion）、**MR**（memory region，注册与 lkey/rkey）、doorbell。一次 RDMA write 的完整旅程走一遍。
  3. 操作语义：**two-sided**（send/recv，需对端配合）vs **one-sided**（read/write，对端 CPU 无感）——对系统设计的含义（KV 存储、参数服务器爱用 one-sided；NCCL 主要用哪种一句话预告 L38）。
  4. 传输类型：**RC**（可靠连接，主流）/UC/UD 一句话各；RC 的**有序可靠假设**与 **go-back-N** 重传 → 「丢一个包代价巨大」→ 这是 L30 无损网络的全部动机（关键伏笔，务必点透）。
  5. 两大阵营：**InfiniBand**（原生 RDMA、credit-based 流控、集中式 subnet manager；世代 EDR/HDR/NDR/XDR，03 表）vs **RoCEv2**（RDMA over UDP/IP over Ethernet——复用以太网生态但要自己解决丢包，L30）；iWARP 一句话（凉了）；选型现实：NVIDIA 系集群多 IB，超大厂自建多 RoCE（成本与可控性）；**EFA**（AWS 的 SRD 传输，乱序容忍思路提名，L32 回收）。
  6. **GPUDirect RDMA**：网卡 DMA 直达 GPU 显存（绕开主机内存往返）——AI 集群的标配；数据路径图对比（有/无 GDR）。
- **必收术语**：RDMA、kernel bypass、zero copy、verbs、QP、WR/WQE、CQ/CQE、MR、lkey/rkey、doorbell、send/recv、RDMA read/write、one-sided/two-sided、RC/UC/UD、go-back-N、InfiniBand、subnet manager、credit-based flow control、RoCE/RoCEv2、iWARP（认名）、EFA/SRD（提名）、GPUDirect RDMA、NIC/HCA、ConnectX（认名）。
- **定量环节**：时延对比账：内核 TCP 单向 ~30–100 µs vs RDMA ~1–3 µs；对 all-reduce 的意义：p=1024 的 latency 项 α×2(p-1)（预告 L37 公式）在两种传输下差两个量级。再算 GDR 省掉的拷贝：无 GDR 每条消息多走 2 次 PCIe + 1 次主机内存往返。
- **图示**：① TCP 路径 vs RDMA 路径对比图（标出内核/拷贝被绕开处，本课主图）；② verbs 对象关系图（QP/CQ/MR）；③ GPUDirect RDMA 数据路径图。
- **延伸阅读**：《RDMA over Ethernet for Distributed Training at Meta Scale》（SIGCOMM 2024——工业界 RoCE 集群的第一手材料，本模块核心读物；题名以正式发表版为准）；RDMAmojo 博客（Dotan Barak，verbs 细节字典，备查）。
- **误区**：「RDMA 就是快一点的 TCP」——编程模型、可靠性假设、故障模式全不同；「RoCE = IB」——链路层生态完全不同，RoCE 的痛苦（L30）IB 没有；「one-sided 一定更快」——省 CPU 不等于省时延，场景依赖。

## L30 无损网络与拥塞控制

- **文件**：`M4 数据中心与网络/L30 无损网络与拥塞控制.md`
- **定位**：RoCE 集群的核心矛盾课：RDMA 想要不丢包 → PFC → PFC 的并发症 → DCQCN 等 CC 来减少 PFC 触发 → 以及「干脆容忍丢包」的新学派。这是网络方向读者未来最可能发论文的领域之一，讲深一点。
- **前置**：[[L29 RDMA原理]]
- **核心问题**：① 为什么 RoCE 要求「无损」以太网？② PFC 会引发什么系统性风险？③ DCQCN 在 PFC 之前做什么？④ 为什么 2023 后出现「有损 RDMA」潮流？
- **内容要点**：
  1. 动机链条（承接 L29 伏笔）：RC + go-back-N → 丢 1 包重传一窗口 → 吞吐崩塌 → 要求链路层不丢包。
  2. **PFC** 机制：per-priority 的逐跳 PAUSE（8 个优先级队列、XOFF/XON 水线、headroom buffer 计算）；**副作用四件套**：**HoL blocking**（同优先级无辜流被堵）、**congestion spreading**（反压逐跳蔓延）、**PFC storm**（异常端点反压风暴瘫痪全网）、**PFC deadlock**（环形依赖死锁，CBD 概念）。每个配一张小示意图，这些是论文高频词。
  3. **ECN + DCQCN**：交换机在过水线时标记 ECN → 接收端 CNP 通知发送端降速 → 让「端到端减速」跑在「逐跳暂停」前面；水线调参的两难（标早了吞吐低、标晚了 PFC 起飞）；提名同类：**TIMELY/Swift**（延迟信号派）、**HPCC**（INT 精确遥测派）——各一句话定位。
  4. **incast**：AI 集群的典型触发场景（all-to-all、参数服务器聚合、分布式存储读）；为什么 buffer 越大越不是解药（bufferbloat 一句话）。
  5. 「有损学派」：**IRN**（NSDI 2018 思想：选择性重传替代 go-back-N，放松无损要求）→ 工业落地：AWS **SRD**、Google **Falcon**、**Ultra Ethernet（UEC）**——2024–2026 的标准化大事（多路径、乱序容忍、现代重传、libfabric 接口；标注「快速演化区，读最新 spec」）。叙事线：**「把可靠性从网络还给端点」**。
  6. 工程现实一段话：无损域规模上限、PFC 风暴演练、监控哪些计数器（pause 帧数/ECN 标记率）——读工业论文时的「运维味」词汇。
- **必收术语**：lossless network、PFC、priority/traffic class、XOFF/XON、headroom buffer、HoL blocking、congestion spreading、PFC storm、PFC deadlock、ECN、CNP、DCQCN、TIMELY/Swift（认名）、HPCC/INT（认名）、incast、buffer/queue depth、bufferbloat（一句话）、selective retransmission、IRN（认名）、SRD、Falcon（认名）、Ultra Ethernet Consortium（UEC）、libfabric（提名）。
- **定量环节**：PFC headroom 估算：100 m 光纤 RTT ≈ 1 µs，400G 链路 1 µs 在途 ≈ 50 KB + MTU 余量 → 每端口每优先级预留 ~百 KB 级 buffer；一台 64×400G 交换机总 buffer 几十 MB → 「buffer 是稀缺资源」的量化体感。再算 incast：256 打 1，每流 1 MB，末跳 400G → 排空需 5.1 ms，期间 p99 时延爆表。
- **图示**：① PFC 反压链与死锁环示意（本课主图）；② DCQCN 控制环（ECN 标记→CNP→降速）；③ 时间线图：拥塞出现→ECN 生效→PFC 兜底 的层次关系。
- **延伸阅读**：《Congestion Control for Large-Scale RDMA Deployments》（SIGCOMM 2015，DCQCN 原文，重点读 motivation）；《Revisiting Network Support for RDMA》（SIGCOMM 2018，IRN，「有损学派」宣言）；UEC 官网概览白皮书（2024–2026 动向）。
- **误区**：「无损 = 不拥塞」——只是不丢，拥塞变成排队与反压；「PFC 是坏东西」——是特定假设下的合理设计，坏的是滥用；「买大 buffer 交换机就行」——加深队列 = 加长时延，治标不治本。

## L31 AI集群网络拓扑

- **文件**：`M4 数据中心与网络/L31 AI集群网络拓扑.md`
- **定位**：拓扑动物园导览 + 「拓扑要匹配流量」的设计哲学。课题组做拓扑感知调度的直接背景课。
- **前置**：[[L28 数据中心网络基础]]、[[L25 节点内互联]]
- **核心问题**：① 除了 fat-tree 还有哪些拓扑、各自解什么问题？② rail-optimized 是什么、为什么成了 GPU 集群标配？③ 光交换（OCS）为什么在 AI 时代翻红？
- **内容要点**：
  1. 设计哲学开宗明义：拓扑没有最优只有匹配——匹配**流量模式**（all-reduce 的环/树 vs all-to-all 的全互联需求）、**规模**、**成本**（光模块占集群网络成本大头）。
  2. **rail-optimized fat-tree**（现代 GPU 集群标配，重点讲透）：每节点 8 GPU 各配一 NIC，全集群所有「第 i 号 NIC」连到同一组 **rail** 交换机 → 同号 GPU 间一跳可达；为什么与 NCCL 的 PXN 配合（预告 L38）；**rail-only** 激进版（干掉 spine 层，跨 rail 流量走节点内 NVLink 中转——省 25–40% 网络成本，读一篇论文的机会，正式版题名见延伸阅读）。
  3. **Dragonfly（+）**：分组全互联 + 组间少跳，HPC 血统（Slingshot）；自适应路由是它的灵魂伴侣（预告 L32）。
  4. **Torus**：TPU 的 3D torus；wrap-around 链路；与 fat-tree 的本质 trade：邻居通信便宜、任意点对点贵 → 「拓扑与集合通信算法 co-design」的活教材（ring/torus allreduce 天然贴合）。
  5. **光电路交换 OCS**：TPUv4 的 palomar OCS 与 Google Jupiter 演进——电分组交换 vs 光电路交换的本质区别（无排队但重构慢）；用途：拓扑重构（按作业形状拼 torus 切片）、故障绕行、渐进扩容；「毫秒级重构 + 小时级作业 = 绝配」。
  6. NVLink domain 作为拓扑层级（回收 L25 NVL72）：集群 = NVLink 域（柜内）+ scale-out 网（柜间）的两级世界，未来趋势一句话。
  7. 收尾表：五种拓扑 × （对分带宽/直径/成本/适配流量/代表系统）对照表。
- **必收术语**：rail、rail-optimized topology、rail-only、dragonfly、group/global link、torus、wrap-around、OCS（optical circuit switch）、MEMS（一句话）、topology reconfiguration、diameter、path diversity、oversubscribed spine、Slingshot（认名）、Jupiter（认名）、topology-aware（预告 L35/L47）。
- **定量环节**：成本粗账：万卡集群 3 层 fat-tree 全光需 ~5–10 万只光模块量级（每只数百美元）→ 网络占集群成本 10–20%；rail-only 砍掉 spine 后省多少（按论文口径复算）。再算 torus 直径：16×16×16 的 3D torus 最远 24 跳 vs 同规模 fat-tree 5 跳——「省钱买了跳数」。
- **图示**：① rail-optimized 结构图（8 rail，本课主图）；② dragonfly 分组示意；③ 3D torus 与 OCS 重构示意；④ 五拓扑对照表。
- **延伸阅读**：《Rail-only: A Low-Cost High-Performance Network for Training LLMs with Trillion Parameters》（rail-only 正式版题名）；《TPU v4》（ISCA 2023，OCS+torus 实战）；Alibaba HPN（SIGCOMM 2024，双 ToR/双平面的工业答卷，L32 也用）。
- **误区**：「fat-tree 无收敛 = 无拥塞」——ECMP 冲突照样堵（下课主角）；「拓扑越花哨越好」——工业界的胜者是「简单 + 可运维」；混淆物理拓扑与逻辑拓扑（NCCL ring 是逻辑环，铺在物理树上）。

## L32 路由与负载均衡

- **文件**：`M4 数据中心与网络/L32 路由与负载均衡.md`
- **定位**：AI 网络的「一号性能杀手」课：ECMP 哈希冲突。从冲突的数学到五大解法路线，全是近三年顶会论文的主战场。课题组最可能直接引用的一课。
- **前置**：[[L31 AI集群网络拓扑]]、[[L28 数据中心网络基础]]
- **核心问题**：① 多路径明明够用，为什么两条大象流会挤在同一条链路上？② flowlet、packet spraying、adaptive routing 各自怎么解？③ 乱序为什么是包级负载均衡的税，谁来交？
- **内容要点**：
  1. **ECMP** 机制与它的隐含假设：五元组哈希 → 假设「流多且小」→ 统计均匀；AI 流量捅破假设：每 GPU 常常只有 1–4 条长肥流（**low entropy**）→ 生日悖论级碰撞概率 → 某链路 2× 负载 → 该链路上的 collective 全员等它（**straggler 放大**，回收 L28）。
  2. 解法路线图（本课主体，每路线：机制 + 代表系统 + 代价）：
     - **加熵**：多 QP/多源端口拆流（NCCL 的 split 一句话）；代价：连接状态×N。
     - **flowlet switching**：利用突发间隙换路（CONGA 血统一句话）；对持续满速的 AI 大流「无隙可乘」的局限。
     - **packet spraying**（包级喷洒）：逐包换路 → 完美均衡 + 大规模乱序 → 需要 NIC 硬件重排（ConnectX-7 的乱序 RDMA 支持）或协议容忍（SRD/UEC，回收 L30）。
     - **adaptive routing**：交换机按队列深度/链路负载动态选路（IB AR、Spectrum-X、dragonfly 的 UGAL 一句话）；全局 vs 局部信息的两难。
     - **集中式/静态规划**：训练流量可预测（集合通信模式编译期已知！）→ 控制器直接排流量表（TE 思路；预告「集合通信与路由联合优化」research 线，接 L37/L67）。
  3. 双平面/双 ToR 工程流派：Alibaba HPN 的做法——用架构设计减少对动态 LB 的依赖（「消灭问题而不是解决问题」）。
  4. 乱序税的分账：谁重排（NIC 硬件 / 传输协议 / 应用层）；RC 语义 vs 乱序到达的冲突（回收 go-back-N）；「message 语义天然容忍乱序、byte-stream 不容忍」的深层原因。
  5. 评价指标与实验方法：链路利用率分布、FCT、collective bus bandwidth（预告 L37/L39 的 nccl-tests 实测视角）。
- **必收术语**：ECMP、five-tuple hash、hash collision、flow entropy、elephant flow（回收）、flowlet、packet spraying/per-packet load balancing、out-of-order delivery、reordering、adaptive routing、UGAL（认名）、Spectrum-X（认名）、traffic engineering（TE）、dual-plane/dual-ToR（认名）、QP scaling/multi-pathing、in-order delivery guarantee。
- **定量环节**：哈希冲突概率：8 条流随机哈希进 8 条等价链路，至少两流同链路的概率 = 1 − 8!/8⁸ ≈ **99.8%**（生日悖论算给看）；4 流 16 链路 ≈ 31%。冲突后果：链路 2× 订阅 → all-reduce 完成时间 ×2（同步语义）→ 全作业 MFU 直接掉——把「一次哈希不走运 = 烧掉几千卡时」的链条算通。
- **图示**：① ECMP 冲突示意（两大流撞一链路，本课主图）；② 五路线解法谱系图（机制×代价矩阵）；③ packet spraying 乱序重排示意。
- **延伸阅读**：Alibaba HPN（SIGCOMM 2024，必读——工业界视角的问题陈述极佳）；Meta RDMA at scale（SIGCOMM 2024，其 LB 实践节）；《On the Impact of Packet Spraying in Data Center Networks》或近年 UEC 相关综述（选读）。
- **误区**：「多路径 = 自动均衡」——ECMP 只保证哈希均匀不保证负载均匀；「乱序是网络 bug」——是包级 LB 的必然代价，问题只是谁付账；「AI 流量不可预测」——恰恰相反，集合通信是最可预测的流量（这正是研究机会）。

## L33 在网计算与智能网卡

- **文件**：`M4 数据中心与网络/L33 在网计算与智能网卡.md`
- **定位**：「网络不只是管道」专题：交换机做归约（SHARP/SwitchML）、可编程数据面（P4）、DPU 卸载。术语扫盲 + 批判性评估「什么时候 INC 真的赚」。
- **前置**：[[L29 RDMA原理]]、[[L36 集合通信原语]] 可后补（若按顺序学则预告 all-reduce 语义即可）
- **核心问题**：① 交换机怎么帮忙做 all-reduce、能省多少？② P4/可编程交换机给研究者开了什么脑洞？③ DPU 到底 offload 了什么？
- **内容要点**：
  1. **in-network aggregation** 直觉：all-reduce 的数据反正都路过交换机 → 让交换机边转发边求和 → 理论收益：跨网流量减半（每链路只走一遍上行聚合+一遍下行广播）、免去端侧多轮归约的时延。
  2. **SHARP**（IB 生态的官方答案）：交换机内聚合树、streaming aggregation；**NVLS**（NVSwitch 上的同族能力，节点内多播/归约，NCCL 自动启用一句话）；适用面：小消息 latency 优化明显、大消息带宽收益有限的辩证（结合 L37 代价模型预告）。
  3. **可编程数据面**：**PMA/RMT 架构与 P4 语言**一段话（match-action 流水线、寄存器、有限算力/存储的约束）；学术代表：**SwitchML**（NSDI 2021，交换机聚合梯度，float→定点的 trick）、**ATP**（NSDI 2021，多租户聚合）；批判性一段：浮点/大消息/内存限制为什么让「交换机训练加速」落地有限——但作为研究思维训练极佳。
  4. **DPU/SmartNIC**（BlueField 系）：卸载什么（网络虚拟化/存储协议/安全/RDMA 传输本身）；「主机数据面归 DPU、GPU 数据面归 GPU」的分工趋势；对 AI 集群的现实意义：安全隔离多租、存储加速（NVMe-oF 一句话）、以及研究提名「用 DPU 做通信调度/聚合」的论文方向。
  5. 冷静收尾：INC 的普适障碍（异构生态、故障域扩大、调试困难、与加密冲突）——「为什么十年了还没统治世界」，帮读者建立技术评估品味。
- **必收术语**：in-network computing/aggregation、SHARP、streaming aggregation、NVLS、programmable switch、P4、match-action、RMT（认名）、Tofino（认名，已停产的行业事件一句话）、SwitchML（认名）、ATP（认名）、DPU、SmartNIC、BlueField（认名）、NVMe-oF（提名）、offload、multicast、reduction tree。
- **定量环节**：SHARP 收益上限账：ring all-reduce 每 rank 收发 2n(p−1)/p ≈ 2n；理想在网聚合每 rank 只收发 n（上行一份+下行一份）→ 带宽项收益上限 **2×**；latency 项：树深 log 级 vs 环的 p 级——结论：小消息/大 p 时 SHARP 香，大消息时顶多 2×。用 03 口径算一个 1024 卡、1 GB 梯度的具体例子。
- **图示**：① 交换机内聚合树示意（上行求和/下行广播，本课主图）；② DPU 在服务器里的位置图（主机-DPU-网络三明治）。
- **延伸阅读**：《Scaling Distributed Machine Learning with In-Network Aggregation》（SwitchML，NSDI 2021，读 design）；NVIDIA SHARP 技术白皮书/文档（工程视角）；《ATP: In-network Aggregation for Multi-tenant Learning》（NSDI 2021，选读）。
- **误区**：「在网聚合能省 p 倍流量」——上限是 2×（对 ring 而言）；「可编程交换机无所不能」——算力/内存/浮点支持都极受限；「DPU = 更贵的网卡」——它是带完整 OS 的独立计算域，安全/运维含义完全不同。

## L34 存储与数据供给

- **文件**：`M4 数据中心与网络/L34 存储与数据供给.md`
- **定位**：被网络研究者忽视但故障率贡献极高的一条腿：训练数据管线、并行文件系统、checkpoint 洪峰。读懂 MegaScale/Llama-3 论文里 storage 段落所需的全部词汇。
- **前置**：[[L27 走进AI数据中心]]、[[L14 预训练]]
- **核心问题**：① 15T token 怎么喂进一万张嘴而不噎住？② checkpoint 写入为什么会打崩存储、怎么救？③ Lustre/GPFS/对象存储/3FS 各是什么角色？
- **内容要点**：
  1. 三种存储 workload 画像（本课骨架）：**数据读取**（顺序大读、可预取、带宽型）、**checkpoint 写**（周期性全员同时猛写、突发型——「存储侧的 incast」）、**模型分发/加载**（推理侧一对多读，L61 回收）。
  2. 数据管线全程：原始数据 → 离线 tokenize/shuffle → 训练时 dataloader 逐 shard 流式读 + 预取 + 本地缓存；**global shuffle vs shard-local shuffle** 的权衡一句话；dataloader stall 如何被 profiler 抓到（预告 L52）。
  3. 存储家族速览表：本地 NVMe（每节点缓存层）、**并行文件系统**（Lustre/GPFS：条带化、POSIX、元数据服务器瓶颈概念）、**对象存储**（S3 语义、扁平命名空间；一致性注意：AWS S3 自 2020 年底起提供强读后写一致性，旧资料的「最终一致」说法已过时）、内存/近计算缓存（Alluxio 类、DeepSeek **3FS** 提名——为随机读训练样本设计的 NVMe+RDMA FS）。每类：语义/带宽特征/在管线中的位置。
  4. **checkpoint 工程**（重点，衔接 L53）：体积账（checkpoint ≈ **14 B/参数**：BF16 参数 2 + FP32 master/m/v 各 4，**不存梯度**——与训练驻留显存的 16 B/参数区分开，口径见 [[03 约定与符号]] → 405B ≈ 5.7 TB/份）；全员同步写的洪峰带宽需求；缓解术语预告：**async checkpoint**、**sharded checkpoint**、in-memory 多副本（Gemini 思路）、增量/差分。恢复侧：**restore 风暴**（万卡同时读同一份 ckpt）→ P2P 分发。
  5. 网络视角收尾：存储流量走哪张网（front-end 或独立 storage 网）；GPUDirect Storage 一句话；「存储带宽 = 恢复时间 = 生存性」的等式（课题组方向直接接口）。
- **必收术语**：data pipeline、dataloader stall、prefetch、shard、sequence packing（提名）、parallel filesystem、Lustre/GPFS（认名）、striping、metadata server、POSIX semantics、object storage、S3（语义）、NVMe、burst buffer、page cache、checkpoint size、async/sharded checkpoint（预告）、restore、GPUDirect Storage（提名）、3FS（提名）。
- **定量环节**：checkpoint 洪峰：405B 模型 ≈5.7 TB（14 B/参数），若每 30 分钟存一次、要求 5 分钟内写完 → 需 ~19 GB/s 聚合写带宽；恢复侧：万卡各读 5.7 TB 中自己的分片 + 分发放大 → 为什么「从对象存储裸拉」要几十分钟而 P2P/内存方案要秒级——算出两个方案的时间差，读者第一次感受「checkpoint 策略 = 可用性」。
- **图示**：① 训练数据管线图（对象存储→PFS→本地 NVMe→内存→GPU）；② checkpoint 洪峰时序图（周期性尖峰打在存储带宽天花板上）。
- **延伸阅读**：MegaScale（NSDI 2024）与《The Llama 3 Herd of Models》的 infrastructure/storage 段落（对照读）；DeepSeek 3FS 开源仓库 README（体会为 AI 定制 FS 的设计取舍）。
- **误区**：「存储是运维问题不是研究问题」——checkpoint/恢复直接决定生存性指标，是 SOSP/NSDI 常客；「带宽够就行」——元数据风暴、长尾抖动同样致命；把「数据集大小」误当「训练时存储压力」（读是稳态，写洪峰才要命）。

## L35 GPU集群调度

- **文件**：`M4 数据中心与网络/L35 GPU集群调度.md`
- **定位**：从「一个作业怎么跑」抬升到「一千个作业怎么分蛋糕」。Slurm/K8s 词汇、gang scheduling、碎片与公平性——课题组资源效率方向的直接背景。
- **前置**：[[L27 走进AI数据中心]]
- **核心问题**：① 为什么 GPU 作业要 gang scheduling、它引发什么连锁问题？② 你的作业排队三天没跑，集群却显示利用率 60%——怎么回事？③ 调度器优化什么目标：利用率、公平、还是 JCT？
- **内容要点**：
  1. GPU 作业的调度特殊性（对照传统批处理）：**gang scheduling**（512 卡要么全给要么不跑——集合通信的同步语义决定的）→ 排队 head-of-line、资源碎片、饥饿三连锁。
  2. 调度器双雄：**Slurm**（HPC 血统：partition/QoS/backfill/预留）与 **Kubernetes**（云血统：device plugin、Volcano/Kueue 补 gang 语义）；名词各一句话，读论文认得出即可。
  3. **碎片（fragmentation）**：8 卡节点上散着 2+3 卡的作业 → 新来的 8 卡作业进不去；**topology-aware placement**：同作业尽量同 leaf/同 rail（跨 spine 的 all-reduce 慢多少 → 回收 L31/L32）；「调度即拓扑装箱」的观念。
  4. 多租户蛋糕学：**quota**、**preemption**（抢占与被抢者的 checkpoint 联动，预告 L66 弹性训练）、公平性概念速览（DRF 一句话）、**backfill**（用小作业填等待窗）。
  5. 利用率黑话辨析：**allocation rate**（分出去多少）vs **utilization**（分出去的在干活吗，回收 L22 的 MFU 批判）——「60% 分配率 + 40% MFU = 集群真实产出 24%」的乘法。
  6. 学术谱系一段话（每篇一句）：Gandiva（内省+迁移）、Tiresias（信息缺失下的调度）、Pollux（协同调 batch size 与资源，goodput 概念的调度版）、Sia（异构感知）——「读者未来综述的种子清单」。
  7. GPU 共享技术提名：**MIG**（硬切）、**MPS**（软共享）、time-slicing——推理集群常客（L61/L66 回收）。
- **必收术语**：job scheduler、gang scheduling、all-or-nothing、queueing delay、JCT（job completion time）、makespan（提名）、Slurm、partition、backfill、Kubernetes、device plugin、Volcano/Kueue（认名）、quota、preemption、starvation、DRF（认名）、fragmentation、topology-aware placement、bin packing、allocation vs utilization、MIG、MPS、time-slicing。
- **定量环节**：碎片损耗估算：1024 卡集群、作业尺寸混合（1/2/4/8 卡）随机到达，简化模型算出稳态下 10–25% 卡因碎片闲置（给一个可手算的小例子而非仿真）；再算 topology 收益：同 leaf 内 all-reduce vs 跨三层的 α 项差异（引 L37 公式预告）——「放置错位 = 每一步都多付时延税」。
- **图示**：① gang scheduling 排队甘特图（大作业等待造成的空洞）；② 碎片示意（节点装箱图）；③ allocation vs utilization 双层柱状示意。
- **延伸阅读**：《Gandiva: Introspective Cluster Scheduling for Deep Learning》（OSDI 2018，开山）；《Pollux》（OSDI 2021 best paper，goodput 调度）；Philly trace 论文《Analysis of Large-Scale Multi-Tenant GPU Clusters for DNN Training Workloads》（ATC 2019，配套公开 trace，L67 复用）。
- **误区**：「集群利用率高 = 管理得好」——可能是排队惨烈的另一种说法；「调度是工程活不是科学」——Pollux 级的「调度×训练动力学」联合优化恰是顶会宠儿；「抢占很残忍」——配合 checkpoint/弹性它是资源效率的核心杠杆。
