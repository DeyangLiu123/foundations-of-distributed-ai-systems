# M8 推理系统 · 设计稿

> 模块目标：课题组分布式推理主线的主场模块。从单请求的性能第一性原理（L55）到集群级 serving（L61），把 vLLM/SGLang/Mooncake 时代的论文语言全部铺平。贯穿三个角色的视角切换：**用户要时延、平台要吞吐、SLO 是两者的契约**。

## L55 推理性能模型

- **文件**：`M8 推理系统/L55 推理性能模型.md`
- **定位**：M8 的第一性原理课：用 roofline（回收 L23）把 prefill/decode 的性能上限算到底，正式建立 TTFT/TPOT/goodput/SLO 指标体系。后面七课全部踩在这一课上。
- **前置**：[[L13 自回归生成与KV缓存]]、[[L23 Roofline模型]]
- **核心问题**：① 为什么 prefill 吃算力、decode 吃带宽（定量证明）？② TTFT/TPOT/E2E 怎么定义、由什么决定？③ batch size 对两阶段各有什么影响、goodput 为什么是「带 SLO 的吞吐」？
- **内容要点**：
  1. 两阶段的 roofline 定位（本课高光推导）：prefill = S 个 token 并行过一遍 = 大 GEMM，AI ≈ S 级 → compute-bound；decode = 每 token 读全部权重+KV cache 只算 2N FLOPs，AI ≈ 1 → 深度 memory-bound；**decode 吞吐上限 = 显存带宽 ÷ (权重+KV 字节)** 公式立起（回收 L21 的 209 tok/s 例子并正式化）。
  2. 指标体系（正式定义 + 图示一条请求的时间线）：**TTFT**（首 token，≈ 排队+prefill）、**TPOT/ITL**（token 间隔，≈ decode 每步）、E2E latency = TTFT + TPOT×输出长度；吞吐（tokens/s、requests/s）；**SLO**（如 TTFT<2s ∧ p99 TPOT<50ms）；**goodput = 满足 SLO 的有效吞吐**（DistServe 语义）——「加 batch 吞吐涨、TPOT 也涨，货真价实的 tradeoff」曲线。
  3. **排队论最小工具箱**（serving 论文的数学母语，全课程只在此正面讲一次）：到达率 λ、服务率 μ、利用率 **ρ=λ/μ** 与稳定条件 ρ<1；**Little's Law**（在飞请求数 = λ × 平均时延——把并发、吞吐、时延焊在一起的万能等式，验证任何 serving 论文数据表的第一工具）；M/M/1 直觉：等待时间 ∝ 1/(1−ρ)，ρ→1 时爆炸——**尾延迟的第一性来源**；burstiness（到达方差）让同样的平均负载更疼。只建直觉与两条公式，不展开排队论课程。
  4. batch 的不对称效应：decode 加 batch ≈ 免费提吞吐（权重读一次摊给 B 个请求 → AI×B，直到转 compute-bound 或 KV 带宽主导）；prefill 加 batch 收益小（本就 compute-bound）——「为什么调度器拼命攒 decode batch」（L57 的理论根据）。
  5. 显存预算式：HBM = 权重 + KV cache（B×每请求 KV）+ activation 零头 → **最大并发 B 的上限公式**（L56 的动机）。
  6. 负载画像：输入输出长度分布（生产 trace 的长尾性）、burstiness、reasoning 负载的输出膨胀（回收 L15：输出 10× → decode 时间主导加剧）——「负载决定架构」的开题（L60 PD 分离的伏笔）。
  7. 成本视角收口：$/M tokens 的构成初算（卡时价 ÷ 吞吐），完整版 L61。
- **必收术语**：TTFT、TPOT/ITL、E2E latency、queueing delay、tokens/s、RPS、SLO、SLA（一句话辨析）、goodput（推理语义）、latency-throughput tradeoff、batch effect、memory-bound decode（回收深化）、compute-bound prefill、concurrency、saturation、workload trace（回收）、reasoning workload、arrival rate（λ）、service rate（μ）、utilization（ρ）、stability condition（ρ<1）、Little's Law、M/M/1（认名）、burstiness。
- **定量环节**（本课灵魂，三连算）：① 70B-BF16、TP8×H100：权重每卡 17.5 GB → decode 单请求上限 ≈ 3350/17.5 ≈ 191 tok/s（忽略 KV/通信 → 再打折）；② 加 KV：B=64、S=4K → KV 总量 ≈ 86 GB（每请求 ≈1.34 GB，L13 公式）；TP8 下 KV 随 8 个 KV 头切到 8 卡 → **每卡 ≈ 10.7 GB**，与每卡 17.5 GB 权重同量级 → 重算上限，体会 KV 挤占（KV 是否随 TP 切分要写明口径）；③ prefill：S=4K 一次 ≈ 2×70e9×4096 FLOPs ÷（8×989T×50%）≈ 145 ms——「TTFT 的物理下限」；④ Little's Law 校验：QPS=10、平均 E2E=6 s → 平均在飞 ≈ 60 个请求——对照 ② 的并发预算判断单实例是否扛得住。全程用 03 口径。
- **图示**：① 一条请求的时间线解剖（TTFT/TPOT 标注，本模块封面图）；② prefill/decode 在 roofline 上的两个点（回收 L23 主图加点）；③ 吞吐-TPOT tradeoff 曲线与 SLO 竖线（goodput 面积直观化）；④ 等待时间 vs ρ 曲线（1/(1−ρ) 爆炸，标注「尾延迟从这里来」）。
- **延伸阅读**：《Transformer Inference Arithmetic》（kipply，回收 L13 推荐，本课工具化）；DistServe（OSDI 2024）的 motivation 节（goodput 定义与两阶段干扰实测——为 L60 预热）；NVIDIA/Databricks 的 LLM inference 性能博客（任选，看图）。
- **误区**：「买算力强的卡提升 decode」——decode 看带宽（H20 反而香，回收 L26）；「吞吐和时延可以同时最优」——tradeoff 曲线上不存在这个点，所以才需要 SLO 语言；「TTFT 只看模型速度」——排队常常才是大头（L57）。

## L56 KV缓存与PagedAttention

- **文件**：`M8 推理系统/L56 KV缓存与PagedAttention.md`
- **定位**：vLLM 革命的解剖课：KV cache 的显存管理从「预留连续大块」到「分页」的范式转移，以及 prefix caching 的复用经济学。serving 论文的核心背景。
- **前置**：[[L55 推理性能模型]]、[[L21 GPU内存体系]]
- **核心问题**：① 朴素 KV 管理浪费在哪（内部/外部碎片）？② PagedAttention 怎么借操作系统的分页思想？③ prefix caching 为什么能把多轮对话成本打下来？
- **内容要点**：
  1. 问题铺陈：生成长度不可知 → 朴素方案按 max_len 预留连续显存 → **内部碎片**（用不满）+ **外部碎片**（长短不齐）→ vLLM 论文实测浪费 60–80% 的历史数字（标注出处）；并发上限被虚占卡死（回收 L55 预算式）。
  2. **PagedAttention**：显存切 **block**（如 16 token/块）+ **block table**（逻辑块→物理块映射）→ 按需分配、零外部碎片；与 OS 虚拟内存的对照表（page/page table/…——给系统背景的读者一次「他乡遇故知」）；attention kernel 要会查表读散块（工程代价一句话）。
  3. 进阶机制：**copy-on-write**（beam/并行采样共享前缀）、**preemption 的两种恢复**（swap 到 CPU vs 重算——回收 L50 的「算 vs 搬」哲学，L57 调度用）；块大小的 trade 一句话。
  4. **prefix caching**：相同前缀（system prompt/few-shot/多轮历史）的 KV 直接复用 → **RadixAttention**（SGLang：radix tree 组织缓存、LRU 淘汰）；命中率决定 TTFT 的数量级差（算例见下）；**cache-aware routing** 预告（L61：把同前缀请求路由到同实例）。
  5. KV 的层级化：显存 → CPU 内存 → SSD/远端（**KV offload/tiering**，Mooncake store 预告 L60、LMCache 认名）；「KV cache 正在变成一个分布式存储系统」——课题组 KV 主线的点题句。
  6. KV 压缩一句话回收（GQA/MLA/量化 → L18/L58），完成「KV 三板斧：省着生成（结构）、管好（本课）、挪走（分层）」的全景。
- **必收术语**：KV cache management、internal/external fragmentation、PagedAttention、block、block table、logical/physical block、copy-on-write、swap vs recomputation、prefix caching、prefix sharing、RadixAttention、radix tree、cache hit rate、eviction/LRU、KV offloading/tiering、LMCache（认名）、vLLM、SGLang。
- **定量环节**：① 碎片账：max_len=4K 预留 vs 实际平均 350 token → 利用率 <10% 的构造例；分页后同显存并发提升的倍数估算；② prefix 命中经济学：32K token 的 system prompt+文档，命中 → TTFT 省一次 32K prefill（用 L55 公式 ≈ 1.2 s 级）+ 省 KV 重算显存；命中率 70% 的集群等效算力放大倍数粗算。
- **图示**：① 朴素 vs 分页的显存布局对比图（本课主图）；② block table 映射图（OS 分页对照版）；③ radix tree 前缀共享示意。
- **延伸阅读**：《Efficient Memory Management for Large Language Model Serving with PagedAttention》（SOSP 2023，vLLM——本模块必读第一篇，配合本课精读 §3–4）；SGLang 论文/博客的 RadixAttention 部分。
- **误区**：「PagedAttention 加速了 attention 计算」——它管显存，吞吐收益来自并发变大（kernel 反而略慢）；「prefix caching 总是赚」——低命中场景纯付管理税；「KV 丢了就完了」——可重算，swap vs recompute 是成本选择不是生死。

## L57 连续批处理与调度

- **文件**：`M8 推理系统/L57 连续批处理与调度.md`
- **定位**：推理引擎的心脏一课：iteration-level scheduling 范式转移（Orca）、chunked prefill 的干扰治理（Sarathi）、抢占与公平。课题组 request routing/batching 研究的直接基础。
- **前置**：[[L55 推理性能模型]]、[[L56 KV缓存与PagedAttention]]
- **核心问题**：① request-level batching 为什么浪费严重？② continuous batching 怎么做到「随到随进、先完先走」？③ prefill 和 decode 同引擎混跑的干扰怎么治？
- **内容要点**：
  1. 静态批的两宗罪（配甘特图）：等齐才开车（新请求等一整批）+ 短请求陪跑到最长者结束——利用率与时延双输；**continuous batching**（Orca 的 iteration-level scheduling）：每个 decode step 都是重新组队的机会，完成即退、新客即入；vLLM/SGLang/TensorRT-LLM 全员采纳 = 「范式」的含义。
  2. 混跑干扰问题：一个新请求的 prefill（重计算）插进 decode 批 → 该步全员 TPOT 尖刺（**generation stall**）；治理谱系：prefill 优先/decode 优先的两难 → **chunked prefill**（Sarathi：把长 prefill 切片、与 decode 拼车 → TTFT 略增换 TPOT 平稳）；「切多大」的 trade 一句话；PD 分离作为终极解的预告（L60）。
  3. 调度策略空间（研究地图式呈现）：FCFS/优先级/**SJF 类**（输出长度未知 → 预测长度的研究线一句话）、多租户公平（fair sharing）、**admission control**（超载时拒绝 vs 全员恶化——回收 L55 goodput 语言）、抢占与降级（回收 L56 swap/recompute）；「调度目标 = maximize goodput s.t. SLO」的形式化一句话。
  4. 引擎主循环解剖（伪代码级，10 行）：waiting/running 队列 → 每步：调度决策（谁进谁出谁抢占）→ 组 batch → 前向 → 采样 → 检查完成——「读懂 vLLM 源码结构」的地图。
  5. 负载现实：burstiness 与队头阻塞；p99 的来源分解（排队为主——用 L55 的排队论语言：ρ→1 时等待 ∝ 1/(1−ρ)，这就是 admission control 存在的数学依据；《The Tail at Scale》认名，L65 精读）；**SLO 分级**（interactive vs batch/offline tier——错峰互补，L61 集群层回收）。
- **必收术语**：request-level/static batching、continuous batching、iteration-level scheduling、in-flight batching（TRT-LLM 同义词）、Orca（认名）、generation stall、chunked prefill、Sarathi（认名）、prefill-decode interference、scheduling policy、FCFS/SJF、admission control、preemption（推理语义）、fairness、queue head-of-line、SLO tier、offline/batch inference。
- **定量环节**：静态批浪费的可复算模型（假设写死）：B=64 一批、输出长度独立同指数分布（均值 350 token）、批内先完成者空转到最长者结束——最长者期望 ≈ 350×H₆₄（调和数 H₆₄≈4.74）≈ 1660 token → 槽位平均利用率 ≈ 350/1660 ≈ 21%，浪费 ≈ **4.7×**；若换「按 max_len=4096 固定预留」的假设则 ≈ 4096/350 ≈ **11.7×**——两种假设都写明；再对照论文实测：vLLM 论文报告相对较强基线 2–4× 吞吐提升、Orca 相对朴素基线倍数更大——落点「倍数永远取决于 baseline 与假设」；chunked prefill 算例：8K prefill 切成 512/chunk 拼进 decode 批 → TPOT 尖刺从 ~600 ms 摊平到 ~60 ms×16 步（用 L55 口径粗算）。
- **图示**：① 静态批 vs 连续批甘特图（本课主图）；② chunked prefill 拼车示意；③ 引擎主循环流程图。
- **延伸阅读**：《Orca: A Distributed Serving System for Transformer-Based Generative Models》（OSDI 2022——continuous batching 出处，精读 §4）；Sarathi-Serve（OSDI 2024）；vLLM 官方文档 scheduler 部分（对照源码地图）。
- **误区**：「batch 越大越好」——TPOT SLO 会先爆（goodput 语言防杠）；「continuous batching 是 vLLM 发明的」——Orca 首创、vLLM 发扬；「prefill 优先天经地义」——interactive 场景 decode 平稳性同样是 SLO，取舍才有研究空间。

## L58 量化推理

- **文件**：`M8 推理系统/L58 量化推理.md`
- **定位**：把 L24 格式知识变成推理降本工具：weight-only vs weight+activation 两条路线、主流方法认名（GPTQ/AWQ/SmoothQuant/FP8）、量化税的评估方法论。
- **前置**：[[L24 数值格式]]、[[L55 推理性能模型]]
- **核心问题**：① 量化为什么能直接提高 decode 吞吐（roofline 复利）？② W4A16 / W8A8 / FP8 这些代号怎么读、各自的难点？③ 「无损」宣称怎么科学地验证？
- **内容要点**：
  1. 复利机制回收（L23/L55）：decode memory-bound → 权重字节减半 = 吞吐近似翻倍 + 显存省一半 = 并发/可部署性双赢——「量化是推理侧性价比之王」；PTQ vs QAT 的成本谱系（大模型时代 PTQ 为主）。
  2. 代号解码器（本课公共服务）：**W{x}A{y}** 记法（W4A16 = 权重 4bit 激活 16bit）；weight-only（W8A16/W4A16：解量化后仍 BF16 算，Tensor Core 不变）vs weight+activation（W8A8/FP8：真 INT8/FP8 GEMM，算力也翻倍）——两路线的收益与难度对照表。
  3. 难点与方法（每个：一句话思想 + 认名）：**outlier** 问题（回收 L24：激活的极端通道让均匀量化崩溃）→ **SmoothQuant**（难度从激活挪去权重）；weight-only 的精细化 → **GPTQ**（逐层最小化重构误差）/ **AWQ**（按激活感知保护重要权重）；**FP8 serving**（Hopper 后的甜点：几乎无损+原生算力）；**KV cache 量化**（回收 L56 三板斧）；极低位 INT4/NVFP4 与 kernel 生态（Marlin 认名）。
  4. **量化税评估方法论**（研究素养重点）：perplexity 差 ≠ 任务无损；评估清单：多任务 benchmark + 长文本 + 生成质量人评；「校准集（calibration set）依赖」与分布外风险；读论文时对「lossless」宣称的三连问。
  5. 部署现实：各引擎支持矩阵速览（认知即可，标注「快速演化区」）；量化与并行的交互一句话（TP 下的 per-channel scale 切分）；蒸馏/剪枝作为压缩家族其余成员各一句话（回收 L15 distillation）。
- **必收术语**：quantization、PTQ/QAT、W4A16/W8A8 记法、weight-only quantization、dequantization、SmoothQuant（认名）、GPTQ（认名）、AWQ（认名）、group size（g128）、calibration、outlier channel（回收）、KV cache quantization、FP8 serving、Marlin（认名）、quantization tax、lossless 宣称、pruning（一句话）、distillation（回收）。
- **定量环节**：8B 模型单卡 H100 三档对比（回收 L24 表并推理化）：BF16 16 GB/209 tok·s⁻¹ ceiling → W8 8 GB/~418 → W4 4 GB/~836；再算并发收益：省下的 12 GB 全给 KV（每请求 S=4K 的 KV 按 L13 公式）→ 并发 +N 个；最后算 $/M tokens 的变化（预告 L61 口径）——「量化的钱账」。
- **图示**：① 两路线（weight-only vs W8A8）数据通路对比图（哪里解量化、哪里真低精度 GEMM）；② outlier 通道直方图示意；③ 量化收益三联柱状（吞吐/显存/成本）。
- **延伸阅读**：《AWQ: Activation-aware Weight Quantization…》（MLSys 2024 best paper，读 motivation 与图）；SmoothQuant（ICML 2023，看核心图）；vLLM 量化支持文档（工程速查）。
- **误区**：「量化必掉点」——W8/FP8 在评估得当下常常测不出差异，W4 才开始付税；「量化提速在所有场景成立」——compute-bound 的大 batch prefill 里 weight-only 几乎不提速（roofline 判断）；「校准随便找点数据」——分布错配是暗坑。

## L59 投机解码

- **文件**：`M8 推理系统/L59 投机解码.md`
- **定位**：用「闲置算力」买时延的代表技术：draft-verify 机制、无损性直觉、接受率经济学、谱系认名（独立 draft/EAGLE/Medusa/MTP）。轻量一课，但术语出镜率极高。
- **前置**：[[L55 推理性能模型]]、[[L13 自回归生成与KV缓存]]
- **核心问题**：① decode 每步只算一个 token 浪费了什么？② 为什么「小模型打草稿+大模型批改」能保证输出分布不变？③ 加速比由什么决定、什么时候会负优化？
- **内容要点**：
  1. 机会识别（roofline 复利第三发）：decode 一步读 140 GB 权重只算 1 token；**同一次读可以顺便验证 k 个 token**（并行 forward k 个位置的边际成本 ≈ 0，memory-bound 区间内）——「白嫖闲置算力」。
  2. **draft-verify 机制**：小模型自回归猜 k 个 → 大模型一次并行 forward 全部验证 → 从左到右接受直到首个分歧 + 大模型免费补一个 → 循环；**无损性**：rejection sampling 保证输出分布 = 大模型独跑（直觉级论证 + 「工程上温度/采样参数影响接受率」备注）。
  3. **接受率经济学**：期望每轮产出 ≈ 接受数+1；加速比公式（简化版：k、接受率 α、draft 开销 c 的函数）；「草稿越像正主越赚」→ draft 来源谱系：独立小模型 / n-gram·prompt-lookup（检索式免模型）/ **self-speculative**（自家浅层）/ **Medusa**（多头并行猜）/ **EAGLE**（特征级自回归，当前主流）/ **MTP**（DeepSeek：训练时就带多 token 预测头——训练-推理 co-design 样本）；树形投机一句话（多分支下注）。
  4. 负优化条件（批判性）：大 batch 高负载时 GPU 已 compute-bound → 验证的「免费」不再成立 → spec-dec 反而降吞吐——「时延优化 ≠ 吞吐优化」的教学时刻（回收 L55 tradeoff）；动态开关的工程实践一句话。
  5. 与其他技术的正交组合表：spec-dec × 量化 × PD 分离 × prefix cache 的兼容性速览（读者拼装系统的思维练习）。
- **必收术语**：speculative decoding、draft model、target model、verify、acceptance rate、rejection sampling（一句话）、lossless（分布保持语义）、n-gram/prompt lookup、self-speculative、Medusa（认名）、EAGLE（认名）、MTP/multi-token prediction、tree speculation/verification、speculation length k。
- **定量环节**：加速比手算（独立接受近似）：k=4、α=70%：期望产出/轮 = 1+α(1−α^k)/(1−α) ≈ **2.77 token**；draft 开销 5%×4 步 + 一次并行验证 → 一轮耗时 ≈ 1.2× 单步 → 加速 ≈ **2.3×**；再算负优化点：batch=64 时 decode 已达 compute 屋顶的 60% → 验证 k=4 使计算需求 ×4 → 超屋顶 → 排队恶化。两道算完，「什么时候开」自明。
- **图示**：① draft-verify 一轮流程图（接受/拒绝分支，本课主图）；② 加速比 vs 接受率曲线族（不同 k）；③ 谱系图（draft 来源分类树）。
- **延伸阅读**：《Fast Inference from Transformers via Speculative Decoding》（ICML 2023，原理出处，读 §2）；EAGLE 论文（选读）；DeepSeek-V3 报告 MTP 节（训练侧视角）。
- **误区**：「投机 = 有损加速」——分布不变是数学保证（这是它对 sampling 语义的最大卖点）；「接受率越高越好，所以 draft 越大越好」——draft 成本吃掉收益，存在最优点；「所有场景都该开」——高负载吞吐场景可能负优化。

## L60 分布式推理与PD分离

- **文件**：`M8 推理系统/L60 分布式推理与PD分离.md`
- **定位**：课题组分布式推理方向的核心课：单机装不下/单机不划算之后的推理并行（TP/PP/EP），prefill-decode 分离架构（DistServe/Mooncake/DeepSeek），KV 传输的网络问题。M8 与 M4/M5/M6 的大会师。
- **前置**：[[L55 推理性能模型]]、[[L47 混合并行组装]]、[[L56 KV缓存与PagedAttention]]、[[L46 专家并行与MoE训练]]
- **核心问题**：① 推理侧的 TP/PP/EP 与训练侧有何不同（latency-bound 通信！）？② 为什么要把 prefill 和 decode 拆到两群机器、代价是什么？③ wide-EP（DeepSeek 推理）为什么是网络系统工程的巅峰样本？
- **内容要点**：
  1. 推理并行三件套复用与变形：**TP**——decode 时每层 all-reduce 的消息极小（b×d 级）→ **latency-bound**（α 主导，回收 L37 小消息世界）→ NVLink/NVLS 的价值再放大；何时用 TP（装不下/压 TPOT）；**PP**——吞吐型、bubble 由 CB 填（推理无同步 flush，比训练友好）；跨机首选；CP 用于超长 prompt 的 prefill 一句话（回收 L45）。
  2. **PD 干扰复盘 → 分离架构**（承接 L57 chunked prefill 的「治标」）：两阶段资源画像完全不同（回收 L55）→ **disaggregation**：P 池（算力型，甚至用 H800/算力卡）+ D 池（带宽型，H20 类卡的舞台——回收 L26 伏笔！）→ 各自最优并行/批策略 + 独立扩缩；代价：**KV cache 要过网**。
  3. **KV 传输工程**（网络研究者的主菜）：一次 4K prompt 的 70B KV ≈ 1.3 GB（算给看）→ 传输通道选择（NVLink 域内 / RDMA 跨机 / CXL 远景）；**layer-wise streaming**（边 prefill 边传边 decode 预热——流水掩盖）；传输库认名：NIXL、Mooncake Transfer Engine；「PD 分离把推理变成了一个流量工程问题」——课题组点题。
  4. **案例双读**：**DistServe**（OSDI 2024：goodput 最优的 P/D 配比与放置——把 L55 指标变成优化目标的范文）；**Mooncake**（Moonshot：KVCache-centric 架构、以缓存池为中心组织 P/D、超售与 SLO 分级——工业级证据；FAST 2025 最佳论文）。
  5. **MoE 推理与 wide-EP**（DeepSeek 开源周的系统课）：MoE decode 的矛盾（37B 激活但 671B 权重都要在线）→ **EP 摊权重**：每卡少数专家、请求 token 经 **A2A** 找专家（回收 L46 但推理版：小消息、时延敏感）→ 大 EP（数十至上百卡）+ **EPLB** 负载均衡 + **DeepEP** 低时延 kernel + **PD 各自的 EP 度**；「batch 越大专家越满 → 吞吐越高 → 所以要把全国流量汇到一个大集群」——规模经济的系统学，也是多集群路由研究的入口（接 L61/L63）。
  6. 收口地图：单卡 → TP 机内 → PP/EP 跨机 → PD 分离 → 多集群多地域（L61/L63/L64）——「推理的分布式化史 = 课题组的研究疆域」。
- **必收术语**：inference parallelism、latency-bound communication、TP for inference、PP for inference、prefill-decode disaggregation（PD 分离）、P/D instance、KV cache transfer、layer-wise streaming、NIXL（认名）、Transfer Engine（认名）、DistServe（认名）、Mooncake（认名）、KVCache-centric、wide-EP/large-scale EP、EPLB（回收）、DeepEP（回收）、prefill/decode instance 配比、heterogeneous deployment（P 用算力卡 D 用带宽卡）。
- **定量环节**：PD 分离的账（本课灵魂）：① KV 传输（拓扑口径写死：TP8 的 P 实例 → TP8 的 D 实例，KV 按 8 个 KV 头分片在 8 卡、每卡配一张 400G NIC）：70B、S=4K → KV 总量 ≈ 1.3 GB；8 个 shard 各走本卡 NIC 并行 → 每卡 ≈0.16 GB ÷ 50 GB/s ≈ **3.4 ms**（并行下界）；若全量汇聚走单条 400G 链路 → ≈ **26 ms**（串行上界）——真实系统落在两者之间（取决于实例放置与网络路径，这正是网络研究者的用武之地），与 prefill ≈ 145 ms（L55 同 TP8 口径）对比：即便取上界也能流水掩盖 → 分离可行性的物理证明；② 干扰消除收益：混跑时 decode p99 TPOT 尖刺（chunked 后仍有 ~15%）vs 分离后平稳 → goodput 提升（引 DistServe 量级：标注以论文为准）；③ wide-EP 直觉账：EP=64 时每卡摊 671B/64 ≈ 10.5B 参数——**BF16 ≈ 21 GB；DeepSeek 实际以 FP8 存放 → ≈ 10.5 GB**（存放精度口径必须写明）→ decode 读权重时间骤降 → 但每层 A2A 两跳 α 税 → 「带宽账换时延账」的平衡点讨论。
- **图示**：① PD 分离架构图（P 池/D 池/KV 流/路由器，本课主图，课题组画 PPT 可直接复用级别）；② layer-wise streaming 流水图；③ wide-EP 的 token→专家 A2A 示意（推理版）。
- **延伸阅读**：DistServe（OSDI 2024，精读）；《Mooncake: A KVCache-centric Disaggregated Architecture for LLM Serving》（arXiv 版题名；FAST 2025 正式版题名有出入，引用以发表版为准。精读——课题组方向必读）；DeepSeek 开源周的推理系统博客/仓库（DeepEP/EPLB/profile 数据，2025）。
- **误区**：「PD 分离总是更好」——短 prompt/低负载时传输与资源碎片反而亏（DistServe 有适用域分析）；「推理 TP 和训练 TP 一样」——消息从 MB 级变 KB 级，瓶颈从 β 变 α，优化手段完全不同；「MoE 推理省卡」——省算力不省显存，wide-EP 是为了摊显存+攒 batch（回收 L17 剪刀差）。
