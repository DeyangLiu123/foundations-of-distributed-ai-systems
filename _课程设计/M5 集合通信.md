# M5 集合通信 · 设计稿

> 模块目标：集合通信是「分布式训练的母语」，也是课题组研究主线之一，必须学到**能计算、能实测**的深度：八大原语的语义烂熟、α-β 代价模型会推、NCCL 输出看得懂。M6 所有并行策略的通信分析都建立在本模块上。

## L36 集合通信原语

- **文件**：`M5 集合通信/L36 集合通信原语.md`
- **定位**：原语字典课。每个原语：图解语义（每个 rank 通信前后各有什么）+ 谁在用它（与并行策略的对照表）。这张对照表是全课程最高频复用的资产之一。
- **前置**：[[L01 全景图]]；建议先读 [[L25 节点内互联]]
- **核心问题**：① all-reduce/all-gather/reduce-scatter/all-to-all 各自「前后状态」是什么？② 它们之间有什么组合/对偶关系？③ 每种并行策略对应哪个原语？
- **内容要点**：
  1. 语境铺垫：**MPI 血统**词汇——**rank**、**world size**、**communicator/process group**、collective vs **point-to-point**（send/recv）；SPMD 编程模型一句话（人人跑同一程序、按 rank 分工）。
  2. 原语图解（本课主体，统一用「4 rank × 数据块」棋盘图，通信前/后两列）：
     - 一对多/多对一：**broadcast**、**scatter**、**gather**、**reduce**；
     - 多对多：**all-gather**（人人集齐全量）、**reduce-scatter**（规约后各拿一片）、**all-reduce**（规约后人人全量）、**all-to-all**（行列转置式交换，强调它与前三者的本质不同：数据是「个性化」的）；
     - **barrier** 一句话。
  3. 结构关系（帮助记忆 + 后面 ZeRO 要用）：**all-reduce = reduce-scatter + all-gather**（图示推导，L37/L42 的钥匙）；all-gather 与 reduce-scatter 互为「对偶」；reduce+broadcast=all-reduce 的朴素版。
  4. **通信量特征表**：每原语在 p 个 rank、总数据 n 下的每-rank 收发量（此处只列结果，推导留 L37）。
  5. **谁在用什么**（黄金对照表，务必做成醒目表格）：DP 梯度同步→all-reduce；ZeRO/FSDP→reduce-scatter + all-gather；TP→all-reduce（fwd）/all-gather+reduce-scatter（带 SP 时）；PP→send/recv；EP（MoE）→all-to-all；CP（Ring Attention）→P2P 环。每行标注「在 L4x 课会展开」。
  6. 真实尺寸体感：DP 同步一次 = 梯度总量（8B 模型 BF16 = 16 GB）；MoE 一层 all-to-all = 每 token k×d×2B——给两三个典型消息尺寸，破除「通信都是小消息」的想象。
- **必收术语**：collective communication、primitive、rank、world size、communicator、process group、point-to-point（P2P）、send/recv、broadcast、scatter、gather、reduce、all-gather、reduce-scatter、all-reduce、all-to-all（A2A）、barrier、SPMD、reduction operator（sum/max）、in-place（提名）。
- **定量环节**：填表练习：p=8、n=16 GB（8B 模型梯度）：all-reduce 每 rank 收发 ≈ 2n(p−1)/p = 28 GB；all-gather（每 rank 持 n/p）收 n(p−1)/p = 14 GB；all-to-all（均匀）收发各 n(p−1)/p。在 400 Gb/s 网卡上各需多少秒——第一次把「一次同步要几百毫秒」算到明处。
- **图示**：① 八原语棋盘图（本课主图，模块封面级质量）；② all-reduce = RS+AG 分解图；③ 并行策略×原语对照表。
- **延伸阅读**：NCCL 官方文档 Collective Operations 页（图很标准）；MPI 教程（LLNL 版）任选原语页对照。
- **误区**：all-gather ≠ all-reduce（无规约）；all-to-all ≠ all-gather（个性化数据 vs 相同数据）；「reduce 会丢信息所以不好」——DP 求和恰恰要的就是规约。

## L37 通信算法与代价模型

- **文件**：`M5 集合通信/L37 通信算法与代价模型.md`
- **定位**：本模块的数学心脏：α-β 模型 + ring all-reduce 完整推导 + 算法选型逻辑（ring vs tree vs 分层）。课题组做通信调度研究的第一性工具。
- **前置**：[[L36 集合通信原语]]
- **核心问题**：① 同一个 all-reduce 为什么有 ring/tree/halving-doubling 好几种算法？② 「带宽最优」「时延最优」分别是什么意思、界在哪里？③ algbw 和 busbw 差在哪？
- **内容要点**：
  1. **α-β 代价模型**：一条消息耗时 T = α + n·β（α=每消息固定开销：软件栈+传播时延；β=1/带宽）；先用它算 P2P，建立「小消息看 α、大消息看 β」的世界观；γ（每字节计算代价）一句话提名。
  2. **ring all-reduce 完整推导**（本课高光，一步步图解）：RS 阶段 p−1 步、每步收发 n/p → AG 阶段再 p−1 步 → 总时间 2(p−1)α + 2n(p−1)/p·β；n 大时逼近 2n·β 且**与 p 无关**——「带宽最优」的含义；n 小时 2(p−1)α 主导——环的死穴。
  3. **tree/double binary tree**：log p 级时延，NCCL 用双二叉树补带宽（一句话机制）；**recursive halving-doubling / Rabenseifner**：log p 步的带宽最优路线（HPC 血统），与 ring 的对比表（步数/每步消息数/对拓扑的要求）。
  4. 带宽下界一段话：all-reduce 每 rank 至少收发 2n(p−1)/p——ring 已到界；「优化不是变魔术，是逼近下界+压 α+匹配拓扑」的方法论。
  5. **分层/拓扑感知算法**：节点内 NVLink 快、节点间网卡慢 → **hierarchical all-reduce**（节点内 reduce → 节点间 all-reduce → 节点内 broadcast）；2D ring；「rail-optimized 拓扑 + 分层算法」的天作之合（回收 L31）；SHARP 在此谱系的位置（回收 L33）。
  6. **algbw vs busbw**（nccl-tests 黑话，正式定义）：algbw = n/T（用户视角）；busbw = algbw × 2(p−1)/p（all-reduce 系数，硬件视角，用于对照线速）；一张系数表（各原语的换算因子）。
  7. all-to-all 的代价特殊性：每 rank 与所有人交换 → 无 ring 式复用可占，天然吃**对分带宽**，且易 incast（回收 L30）——「MoE 为什么是网络杀手」的理论根据。
- **必收术语**：α-β model、latency term、bandwidth term、ring algorithm、tree algorithm、double binary tree、recursive halving/doubling、Rabenseifner（认名）、bandwidth-optimal、latency-optimal、hierarchical all-reduce、2D ring、algorithm bandwidth（algbw）、bus bandwidth（busbw）、message size regime、pipelining/chunking（大消息切块流水，一句话）。
- **定量环节**：三连算（全用 03 口径）：① p=1024、n=16 GB、400 Gb/s：ring all-reduce ≈ 2×16×1023/1024/50 GB/s ≈ 0.64 s（+α 项可忽略）；② 同 p、n=1 MB：α=10 µs 时 2(p−1)α ≈ 20 ms ≫ 带宽项 → 换 tree（2 log₂p·α ≈ 0.2 ms）快百倍；③ 分层：8 卡节点内 NVLink 450 GB/s 先归约，跨 128 节点再 all-reduce → 跨网数据量降为 1/8。三题做完，选型逻辑自然浮现。
- **图示**：① ring RS+AG 逐步棋盘动画式分解（本课主图）；② 「T vs 消息大小」双对数曲线（ring/tree 交叉点）；③ 分层 all-reduce 结构图。
- **延伸阅读**：《Optimization of Collective Communication Operations in MPICH》（Thakur et al.，IJHPCA 2005——算法谱系的正典，选读）；Baidu ring all-reduce 博客（2017，把 HPC 技术带进 DL 的历史节点）；NCCL 文档 performance 页（busbw 定义出处）。
- **误区**：「ring 总是最好」——小消息时延灾难；「加卡通信更快」——all-reduce 带宽项与 p 无关，α 项还变差，快的是**每卡分到的计算**；busbw 高于网卡线速（可能，因为它是折算值——不理解系数就会读错 nccl-tests）。

## L38 NCCL解剖

- **文件**：`M5 集合通信/L38 NCCL解剖.md`
- **定位**：事实标准库的工程课。目标：读懂论文与工程博客里的 NCCL 黑话（channel/protocol/PXN/NVLS），会跑会读 nccl-tests，认识 NCCL 故障的经典形态。为 L39 实践与 L53 可靠性铺路。
- **前置**：[[L37 通信算法与代价模型]]、[[L25 节点内互联]]
- **核心问题**：① NCCL 怎么知道机器长什么样、怎么选算法？② channel/protocol 这些调优黑话什么意思？③ nccl-tests 的输出表怎么读、多少算「打满」？
- **内容要点**：
  1. NCCL 是什么/不是什么：GPU 原生集合通信库（vs MPI 的 CPU 血统）；它把 L37 的算法学变成工程：**拓扑发现**（枚举 NVLink/PCIe/NIC 建图）→ **图搜索**（找环/树）→ **算法+协议选择**（按消息大小查表）。
  2. 执行模型：collective 也是 **CUDA kernel**（SM 上跑通信！与计算抢 SM——通信计算重叠的隐藏代价，预告 L52）；**channel** = 并行通信流水线（多环并发占满多 NIC）；proxy 线程管网络。
  3. **协议三件套**：Simple（大消息带宽型）/ **LL**（low-latency，小消息，8B flag 技巧一句话）/ **LL128**（NVLink 上的折中）——「同一算法×三协议 = 时延带宽菜单」。
  4. 跨机秘技：**PXN**（经 NVLink 中转到同 rail 的 GPU 再出网卡——rail-optimized 拓扑的软件搭档，回收 L31）；**NVLS**（NVSwitch 硬件归约，回收 L33）；GDR 回收（L29）。
  5. 工程接口速览：环境变量家族（NCCL_DEBUG/NCCL_ALGO/NCCL_PROTO/NCCL_IB_HCA/NCCL_SOCKET_IFNAME 等，各一句话用途）；**nccl-tests**：命令行、输出表逐列讲（size/time/algbw/**busbw**）、判断「打满」的参照线（busbw ≈ 网卡线速 ×0.9 为佳）。
  6. 故障经典形态（预告 L53，此处给名词与直觉）：**NCCL timeout**（某 rank 掉队/网络抖动 → 集体等死）、hang（死锁式互等）、WARN 日志的常见原因（GDR 没开/走错网卡/拓扑不对称）。「分布式训练报错十有八九长着 NCCL 的脸，但病根常在别处」。
  7. 生态一句话：RCCL/oneCCL/HCCL（各家等价物）、Gloo（CPU 后备）、MSCCL/MSCCLang（可编程集合通信，研究向提名）。
- **必收术语**：NCCL、topology detection、channel、protocol（Simple/LL/LL128）、proxy thread、PXN、NVLS、GPUDirect RDMA（回收）、nccl-tests、algbw/busbw（回收）、NCCL timeout、rendezvous（初始化语义一句话）、RCCL/HCCL/oneCCL/Gloo（认名）、MSCCL（提名）、CUDA kernel（通信也是 kernel）。
- **定量环节**：读一张真实风格的 nccl-tests all_reduce_perf 输出表（8 节点×8 卡、NDR）：找出 busbw 峰值、对照 50 GB/s×0.9 判断健康；找出小消息区 α 主导的证据（时间不随 size 降而降）。「拿到集群先跑 nccl-tests」的体检习惯。
- **图示**：① NCCL 拓扑发现→建环示意（物理图+逻辑环叠加）；② 协议选择矩阵（消息大小×算法×协议）；③ 注释版 nccl-tests 输出表。
- **延伸阅读**：NCCL 官方文档 + GitHub issues（工程真相集散地）；Sylvain Jeaugey 的 GTC NCCL 演讲（历年，架构演进第一手）；nccl-tests 仓库 README（busbw 公式出处）。
- **误区**：「NCCL 慢就调环境变量」——先跑 nccl-tests 定位是拓扑/网卡/配置哪层的问题；「通信不占 GPU」——NCCL kernel 抢 SM，重叠不是免费的；「timeout 报错 = 网络坏了」——更常见是某 rank 慢/挂导致的集体陪等。

## L39 实践-动手集合通信

- **文件**：`M5 集合通信/L39 实践-动手集合通信.md`
- **定位**：【实践课】笔记本可跑（gloo 后端多进程模拟多 rank），把 L36–L38 变成肌肉记忆：跑原语、验语义、测 α-β、读输出。
- **前置**：[[L38 NCCL解剖]]
- **实践目标（读者要亲眼看到）**：① 8 个进程的 all-reduce 结果 = 各 rank 数据之和；② all-reduce 结果与手工 reduce-scatter+all-gather 两步结果完全一致；③ 实测「时间 vs 消息大小」曲线呈 α 平台 + β 斜线两段式；④ 拟合出本机的 α 和 β；⑤ （有条件者）读懂一份真实 nccl-tests 输出。
- **内容要点**：
  1. 环境：`torch.distributed` + gloo 后端 + `torchrun --nproc_per_node=8`（纯 CPU 可跑；有多卡者附 NCCL 版命令）。
  2. 任务 A（语义验证）：每 rank 造 `tensor([rank])`，依次跑 broadcast/all-gather/reduce-scatter/all-reduce/all-to-all，打印前后状态与 L36 棋盘图对照。
  3. 任务 B（对偶验证）：手写 RS+AG 复现 all-reduce，比对结果——「读懂 ZeRO 的钥匙自己造一遍」。
  4. 任务 C（代价测量）：消息从 1 KB 扫到 64 MB，测均值曲线，log-log 作图，拟合 α（小消息平台）与 β（大消息斜率），与本机内存带宽/回环开销对照解读。
  5. 任务 D（读表）：给一份附带的 nccl-tests 样例输出（设计稿附一份 8×H100 的典型数值表），按 L38 方法判读健康度。
  6. 挑战：模拟 straggler——某 rank sleep 5 ms，测 all-reduce 整体变慢多少（「木桶效应」实证，接 L53）。
- **必收术语**：（复习课；术语卡片改为「亲手验证的 6 个结论」清单）
- **延伸阅读**：PyTorch distributed 官方教程（Writing Distributed Applications）；nccl-tests README。
