# M7 训练工程与可靠性 · 设计稿

> 模块目标：从「并行策略在纸上成立」到「万卡训练在现实中活下来」。前四课是性能工程（精度/显存/算子/剖析），后两课是课题组生存性方向的主场（可靠性）与 2025 后最热的 RL 系统。贯穿指标：**MFU 与 goodput**。

## L49 混合精度与FP8训练

- **文件**：`M7 训练工程与可靠性/L49 混合精度与FP8训练.md`
- **定位**：把 L24 的格式知识变成训练配方：AMP 机制、BF16 时代的标准做法、FP8 训练的前沿工程（DeepSeek 配方）。读懂训练论文 precision 段落所需的一切。
- **前置**：[[L24 数值格式]]、[[L40 训练显存全解剖]]
- **核心问题**：① 「混合」精度到底哪里混合？② FP16 时代为什么需要 loss scaling、BF16 为什么不需要？③ FP8 训练难在哪、DeepSeek 怎么做成的？
- **内容要点**：
  1. **AMP 机制**：低精度算 forward/backward（吃 Tensor Core 峰值）+ **FP32 master weights** 更新（防小梯度被舍入吞掉）——「算得糙、记得精」；哪些算子留 FP32（norm/softmax/loss 的黑名单机制一句话）。
  2. FP16 时代考古：动态范围窄 → 梯度 underflow → **loss scaling**（放大再缩回）与 dynamic scaling；BF16 时代：范围同 FP32 → 免 scaling → 成为默认（回收 L24 的伏笔，闭环）。
  3. **gradient clipping 与 loss spike 处置手册**：grad norm 监控、spike 的常见原因（坏数据/lr/数值）与处置（跳 batch/回滚/降 lr）——读训练日志的「病历」能力（回收 L14）。
  4. **FP8 训练**（前沿主课）：为什么难（动态范围更窄、outlier）；**Transformer Engine** 的 per-tensor scaling + **delayed scaling**（用历史 amax 估当前 scale）；**DeepSeek-V3 配方**精读：细粒度（tile/block-wise）scaling、高精度累加、哪些环节保留 BF16/FP32——「FP8 省一半算力时间但精度工程极重」的辩证。
  5. 低精度的通信面一句话：梯度/参数通信也可低精度（FP8 all-gather 等，ZeRO++ 提名）——带宽减半的诱惑与风险（预告 L63 的通信压缩谱系）。
  6. 可复现性一段话：非确定性来源（atomics/归约顺序）、为什么两次训练曲线不完全重合、determinism 的性能代价。
- **必收术语**：mixed precision、AMP、master weights（回收）、loss scaling、dynamic loss scaling、underflow（回收）、grad norm、gradient clipping（回收）、loss spike（回收深化）、FP8 training、Transformer Engine、amax、delayed scaling、per-tensor/tile-wise scaling、high-precision accumulation、determinism、bitwise reproducibility。
- **定量环节**：精度经济账：H100 上 BF16→FP8 峰值翻倍（989→1979 TFLOPS）；若计算占比 70%，Amdahl 一下端到端理论加速 ≈ 1/(0.3+0.7/2) ≈ 1.54×；再算显存：激活存 FP8 省一半 → 用 L40 公式重算 8B 例子。「为什么大家肯为 FP8 付工程复杂度」。
- **图示**：① AMP 数据流图（哪里 BF16 哪里 FP32，本课主图）；② loss scaling 机制图（FP16 考古）；③ FP8 delayed scaling 时序示意。
- **延伸阅读**：《Mixed Precision Training》（ICLR 2018，正典）；DeepSeek-V3 报告 FP8 训练节（精读）；NVIDIA Transformer Engine 文档。
- **误区**：「混合精度会让模型变差」——master weights 保证了更新精度，配方正确时几乎无损；「BF16 下 loss scaling 还开着」——不需要（很多老代码拖着尾巴）；「FP8 就是把 dtype 换一下」——scaling 策略才是全部难点。

## L50 显存优化技术

- **文件**：`M7 训练工程与可靠性/L50 显存优化技术.md`
- **定位**：并行之外的显存三板斧：重计算（用算换存）、offload（用慢存换快存）、内存池治理。完成 L40 解法地图的最后拼图。
- **前置**：[[L40 训练显存全解剖]]、[[L21 GPU内存体系]]
- **核心问题**：① activation recomputation 省多少、多花多少算？② offload 到 CPU/NVMe 什么时候可行？③ reserved 涨到 OOM 但 allocated 不高——怎么回事？
- **内容要点**：
  1. **activation recomputation**（gradient checkpointing）：只存边界激活、backward 时重跑 forward 补回中间值；**full vs selective**（Megatron 的选择性策略：只重算便宜算子、贵的如 FlashAttention 输出留着——重计算的性价比排序）；HFU vs MFU 在此闭环（回收 L22：重算灌水 HFU）。
  2. 代价核算：full recompute ≈ 多付 1/3 计算（forward 重跑一遍：2N/6N）；selective 典型 <10%；「显存降数倍、时间加一成」的黄金 trade——为什么它是万卡训练默认开启项。
  3. **offload 家族**：ZeRO-Offload（optimizer states→CPU，更新在 CPU 算）/ ZeRO-Infinity（params→NVMe）；可行性判据 = PCIe 带宽 vs 计算时间的赛跑（算例）；「offload 是穷人的并行，也是弹性系统的富矿」（预告 L66）。
  4. **内存池治理**：PyTorch caching allocator 深入（block 分配、split、expandable_segments）；fragmentation 的形成与治理；读 `memory_summary`/snapshot 工具；「OOM 三问」排查树：真不够？碎了？泄漏了？
  5. 其他杂技一句话 each：sequence packing（把短样本拼满 S，省 padding）、CPU activation offload、NVMe KV offload（推理侧预告 L56）。
  6. 收口：把 L40 解法地图打完勾——「显存问题至此有完整工具箱」，附各技术组合使用的典型配置（如 Llama-3：selective recompute + 无 offload；受限集群：ZeRO-3+offload）。
- **必收术语**：activation recomputation/gradient checkpointing、full/selective recomputation、checkpoint boundary、ZeRO-Offload、ZeRO-Infinity、NVMe offload、PCIe bottleneck（回收）、caching allocator（回收深化）、expandable segments、memory snapshot、sequence packing、padding waste。
- **定量环节**：70B、S=8192：full recompute 把 activation 从 ~X GB 压到边界值（按 L40 公式算两档）；时间代价 = 前向重跑 ≈ 总 FLOPs +33%（6N→8N），MFU 表观变化算给看；offload 判据算例（先立规矩：**驻留量 ≠ 传输量**）：ZeRO-Offload 的 12N optimizer states **常驻 CPU、不过 PCIe**，每 step 真正跨 PCIe 的是梯度下行 + 更新后参数上行 ≈ 4N/DP 字节——70B、DP=8 时每卡 ≈ 35 GB ÷ 64 GB/s ≈ 0.55 s，另加 CPU 上的 optimizer 计算时间；与 GPU 每 step ~2 s 对比 → 必须分桶流水重叠才不掉吞吐，并给出「何时 offload 反而变慢」的判据——「offload 不是免费仓库」。
- **图示**：① recompute 的存/算时序对比图（存边界→反向重跑）；② offload 数据流图（GPU-CPU-NVMe 三级）；③ OOM 排查决策树。
- **延伸阅读**：《Training Deep Nets with Sublinear Memory Cost》（2016，重计算开山，选读）；ZeRO-Offload/Infinity 论文（ATC/SC 2021，读架构图）；PyTorch 文档 memory 工具页。
- **误区**：「重计算免费省显存」——加 1/3 计算且抬 HFU 水分；「offload = 无限显存」——PCIe 带宽是硬闸门；「OOM 就开 recompute」——先看碎片，可能一行 expandable_segments 就好。

## L51 算子优化与FlashAttention

- **文件**：`M7 训练工程与可靠性/L51 算子优化与FlashAttention.md`
- **定位**：kernel 层的性能革命课：为什么不改数学只改访存就能快数倍。FlashAttention 的 tiling+online softmax 直觉推导（本课程最深入 kernel 的一课，也到此为止）。
- **前置**：[[L23 Roofline模型]]、[[L11 注意力机制]]
- **核心问题**：① kernel fusion 为什么能加速（roofline 语言）？② FlashAttention 如何做到「exact 但不落地 S×S 矩阵」？③ torch.compile/CUDA Graph 在解决什么？
- **内容要点**：
  1. 复盘朴素 attention 的账（回收 L11/L23）：S×S 矩阵三次 HBM 往返 → AI 低 → memory-bound；「计算免费、搬运昂贵」时代的算子设计观。
  2. **kernel fusion** 通论：省中间结果的 HBM 往返 + 省 launch；典型 fused 算子清单（bias+GeLU、fused LayerNorm、fused AdamW、fused RoPE——读者在框架日志里会见到的名字）。
  3. **FlashAttention 直觉推导**（本课高光，只用「分块 + 流式 max/sum 修正」的语言，不写 CUDA）：tiling 进 SRAM 逐块算 + **online softmax**（增量维护行 max 与归一化和，来块新的就修正旧结果）→ 不落地 S² 矩阵 → 显存 O(S)、HBM 流量大降；backward 用重计算（与 L50 呼应——「FlashAttention 是 recompute 思想的 kernel 级应用」）。
  4. 版本演进一句话 each：FA-2（并行度/工作划分改进）、FA-3（Hopper 异步/FP8）；变体生态认名：xFormers、SDPA（PyTorch 内置入口）。
  5. **CUDA Graph**：把千次 launch 录成一次重放——decode 小 kernel 场景的救星（回收 L20 launch 账）；约束（静态形状）与 vLLM 等的使用一句话。
  6. **torch.compile/Inductor/Triton**：图捕获→自动融合→生成 Triton kernel；Triton 作为研究者写 kernel 的白话文（vs CUDA 的文言文）一句话定位；「编译器能自动做到几成」的现实评估。
  7. 方法论收口：读论文里「we implement custom fused kernels」时该问的三个问题（融合了什么边界？省了几次往返？在 roofline 上挪了多远？）。
- **必收术语**：kernel fusion、fused kernel、memory traffic、FlashAttention、tiling、online softmax、IO-aware algorithm、SRAM tiling（回收 L21）、FA-2/FA-3（认名）、SDPA、xFormers（认名）、CUDA Graph、graph capture/replay、torch.compile（回收深化）、Triton（回收深化）、epilogue fusion（提名）。
- **定量环节**：FlashAttention 的 HBM 流量账（简化版）：朴素 attention 读写 ≈ 3 次 S×S 矩阵 ×2B（S=8192, h=32：~12 GB/层）vs FA 只读写 QKV/O（~0.5 GB 级）→ 流量降 ~20×；在 3.35 TB/s 上换算成时间对比。再算 CUDA Graph：1000 kernel×4 µs launch = 4 ms vs decode 一步计算 ~5 ms——「launch 能吃掉半步时间」。
- **图示**：① fusion 前后 HBM 往返对比图（roofline 点位移动标注）；② FlashAttention 分块流动示意（Q 块×KV 块扫描 + 修正量流动，本课主图）；③ CUDA Graph 录制/重放时序图。
- **延伸阅读**：《FlashAttention: Fast and Memory-Efficient Exact Attention with IO-Awareness》（NeurIPS 2022，读 3.1 节算法框）；Horace He《Making Deep Learning Go Brrrr…》（回收 L23 推荐，本课再读一遍会有新感受）；Triton 官方 tutorial 第一课（可选动手）。
- **误区**：「FlashAttention 是近似/有损的」——exact，误差只在浮点归约顺序级；「fusion 万能」——compute-bound 的大 GEMM 融了白融（roofline 判断先行）；「编译器会淘汰手写 kernel」——最后 20% 性能与新算子仍靠人（FA 本身就是明证）。

## L52 性能剖析与MFU核算

- **文件**：`M7 训练工程与可靠性/L52 性能剖析与MFU核算.md`
- **定位**：方法论课：拿到一个「训练慢」的系统，如何像医生一样确诊。timeline 判读五大病征 + 端到端 MFU 核算流程。课题组做性能研究的日常技能。
- **前置**：[[L22 算力度量与MFU]]、[[L38 NCCL解剖]]、[[L44 流水线并行]]
- **核心问题**：① profiler 的 timeline 怎么看（哪些行、哪些颜色、找什么）？② 「计算没打满」的五种典型病征各长什么样？③ 从吞吐数字到 MFU 报告的完整核算怎么做？
- **内容要点**：
  1. 工具箱分层：`torch.profiler`（框架级，chrome trace 输出）→ **Nsight Systems**（系统级全景）→ Nsight Compute（单 kernel 显微镜，认名即可）→ DCGM/nvidia-smi（集群监控级）；各看什么/何时用。
  2. **timeline 判读教学**（本课主体，配注释版示意 trace 图）：识别 stream 行、kernel 块、NCCL kernel、memcpy、CPU 侧 gap；五大病征图谱：**dataloader stall**（step 间空白，回收 L34）、**exposed communication**（NCCL 块与计算不重叠，回收 L41/L43）、**pipeline bubble**（回收 L44）、**kernel launch bound**（碎 kernel 海，回收 L51）、**straggler/desync**（多卡 timeline 参差，回收 L46）。每病征：长相 + 确诊法 + 药方链接。
  3. **MFU 核算流程**（端到端模板）：吞吐 tokens/s → ×(6N+attention 项) → ÷卡数÷峰值 → 得 MFU；与分解法交叉验证（各环节耗时占比加总）；常见核算错误清单（用了稀疏峰值/漏了重计算口径 HFU vs MFU/tokens 算成 sequences）。
  4. **goodput 分层**（Meta 语义，预告 L53）：scheduled → available → effective goodput——「MFU 之上还有一层可用性折扣」；两指标合成「集群真实产出」。
  5. 分布式排障一段话：多机 profile 的对时（clock sync）、只看 rank0 的陷阱、NCCL_DEBUG+flight recorder 初探（L53 深化）。
  6. 实操附录：给一段 20 行的 profiler 使用代码模板 + 「拿到 trace 后的 10 分钟检查清单」。
- **必收术语**：profiling、torch.profiler、chrome trace、Nsight Systems/Compute（认名）、DCGM（认名）、timeline、CUDA stream（回收）、gap、dataloader stall、exposed communication、launch-bound、desync、straggler（回收）、MFU accounting、goodput（正式引入）、clock synchronization、flight recorder（预告）。
- **定量环节**：MFU 核算实战题：某 70B 训练、512×H100、实测 4.2×10⁵ tokens/s → 4.2e5×6×70e9=1.76e17 ÷(512×989e12)=**34.8%** MFU；再给病征分解假设（气泡 12%+暴露通信 15%+launch 5%…）验证加总合理性——「审计别人论文的 MFU 声明」的完整武器。
- **图示**：① 注释版 timeline 示意图（五病征各一小图，本课主图群）；② MFU 核算流程图；③ goodput 分层漏斗图。
- **延伸阅读**：PyTorch profiler 官方教程；《The Llama 3 Herd of Models》效率/可靠性段（goodput 语境）；HTA（Holistic Trace Analysis）工具 README（多机 trace 分析，选读）。
- **误区**：「nvidia-smi util 100% = 没问题」（回收 L22，本课用 timeline 实锤）；「profile 一个 step 就够」——warmup/编译/checkpoint step 不代表稳态；「慢一定是通信的锅」——五病征里 dataloader 与 launch 常被冤枉/漏诊。

## L53 大规模训练可靠性

- **文件**：`M7 训练工程与可靠性/L53 大规模训练可靠性.md`
- **定位**：课题组生存性方向的主场课。故障的统计现实（MTBF 数学）、检测（NCCL timeout 解剖）、恢复（checkpoint 工程谱系）、以及 goodput 作为北极星。素材以 MegaScale/Llama-3 的公开数据为骨架。
- **前置**：[[L52 性能剖析与MFU核算]]、[[L34 存储与数据供给]]、[[L38 NCCL解剖]]
- **核心问题**：① 万卡训练为什么「必然」频繁故障（数学上）？② 一次故障从发生到恢复的完整时间线是什么、每段怎么压缩？③ SDC 为什么是最恐怖的故障？
- **内容要点**：
  1. **MTBF 数学**（本课开场暴击）：单卡年故障率 x% → 16K 卡集群 MTBF = 单卡 MTBF/16384 → 用 Llama-3 公开数据反推（54 天 419 次意外中断 ≈ 每 3.1 小时一次，78% 硬件相关——数字标注「以论文为准」）；同步训练的残酷放大：**一卡挂 = 全员停**（gang 语义，回收 L35/L46 straggler）。
  2. 故障分类学（配比例示意）：GPU/HBM 故障、NIC/链路抖动（link flap）、交换机、软件（OOM/死锁）、**SDC**（silent data corruption——算错但不报错：loss 无声漂移、最难检测，一段专讲：成因/检测手段/行业案例）。
  3. **检测与定位**：NCCL timeout 的语义解剖（谁超时≠谁有病——集体等待的连坐效应，回收 L38 伏笔）；心跳/旁路检测、flight recorder、二分定位/演练；「定位耗时常超过修复耗时」的工程现实。
  4. **checkpoint 工程谱系**（恢复时间的分解式：检测 + 定位 + 替换 + 加载 + 重算损失）：同步阻塞式 →**async checkpoint**（后台旁路写）→ **sharded**（各存各的分片，回收 L34）→ **in-memory 多副本**（Gemini：邻居内存互备，秒级恢复）→ 热备节点（hot spare）与快速替换；checkpoint 间隔的优化公式（间隔 vs 重算损失的经典 trade，给 Young/Daly 近似式，**须核实**系数）。
  5. **弹性训练**：故障后不等替换、缩编继续（elastic DP：改 DP 度重配 mesh）；TorchElastic/斜杠社区方案认名；与 L66 的 spot 训练接口。
  6. **goodput 北极星**（收口）：effective training time ratio——Meta/Google 报告口径；把本课所有技术映射为「goodput 分解式里压哪一项」；课题组研究定位：**生存性 = 让 goodput 在故障下不塌**（点题）。
- **必收术语**：MTBF/MTTR、failure rate、interruption、link flap、SDC、fail-stop vs fail-slow（重要区分！）、NCCL timeout（回收深化）、flight recorder、health check、hot spare、checkpoint interval、async/sharded/in-memory checkpoint、Gemini（认名）、elastic training、TorchElastic（认名）、goodput（回收深化）、blast radius（提名）。（推理侧的故障与生存性另有专课 → [[L65 推理服务生存性]]，本课正文结尾要给这个指路。）
- **定量环节**：恢复经济学：16K 卡、每 3 h 一次故障；方案 A（30 min 存一次 ckpt 到 PFS、恢复 20 min）：每次损失 ≈ 平均重算 15 min + 恢复 20 min → goodput ≈ 1−35/180 ≈ 80.6%；方案 B（异步+内存副本：间隔 5 min、恢复 2 min）→ ≈ 97.5%。**一道题算出「checkpoint 工程 = 17 个点的 goodput」**——本课论点的数字化身。
- **图示**：① 故障-恢复时间线解剖图（各段标注可优化技术，本课主图）；② MTBF vs 集群规模曲线（对数轴）；③ checkpoint 谱系演进图。
- **延伸阅读**：MegaScale（NSDI 2024，可靠性章精读）；《The Llama 3 Herd of Models》可靠性段（故障统计表）；《Gemini: Fast Failure Recovery in Distributed Training with In-Memory Checkpoints》（SOSP 2023，选读）。
- **误区**：「故障是运气问题」——是规模的确定性后果，系统必须按「常态故障」设计；「ckpt 越频繁越好」——写入开销与恢复收益的最优点存在；「fail-slow 好过 fail-stop」——恰恰相反，慢而不死最难缠（straggler 连坐）。

## L54 RL后训练系统

- **文件**：`M7 训练工程与可靠性/L54 RL后训练系统.md`
- **定位**：2025–2026 系统顶会最热主题：RLHF/RLVR 的训练-推理混合系统。讲清四模型数据流、colocate vs disaggregate 两大架构、weight sync 与 rollout 长尾两大痛点。读懂 veRL 一族论文的入场券。
- **前置**：[[L15 后训练与对齐]]、[[L47 混合并行组装]]、[[L13 自回归生成与KV缓存]]
- **核心问题**：① 一步 RLHF/GRPO 里，四个模型各干什么、数据怎么流？② 为什么说 RL 训练 = 训练系统+推理系统被迫同居？③ weight sync 和 rollout 长尾各是什么、怎么治？
- **内容要点**：
  1. 回收 L15 的四模型图并系统化：**actor**（被训模型，训练态+生成态双身份！）、rollout/generation（推理引擎跑 actor 生成回答）、**reward/critic/reference** 的前向打分——一步 = **生成阶段（推理 workload）+ 训练阶段（训练 workload）**交替；GRPO 砍掉 critic 的系统减负一句话。
  2. 核心矛盾：两种 workload 的最优系统形态完全不同（推理要 KV cache/大批量/低精度；训练要优化器状态/梯度同步）→ 架构两难：**colocated**（同一批卡轮流干两活：切换开销、显存打架、但资源利用满）vs **disaggregated**（两群卡各干各的：流水但有空转与传输）；两架构图并排对比（本课主图）。
  3. **weight sync 痛点**：每步训练后新权重要发给 rollout 引擎——并行布局还不同（训练 TP8-PP4 → 推理 TP8 或量化布局）→ **resharding** 与广播的通信工程；数字体感（70B 权重 140 GB 的分发）；「参数服务器的幽灵回来了」。
  4. **rollout 长尾**：生成长度方差巨大（同 batch 有人 100 token 有人 10K）→ 同步 RL 里全员等最长者（straggler 的 RL 变体）；治理：continuous batching（回收 L57 预告）、partial rollout、**async RL**（一步旧策略生成 vs 训练并行——off-policy 容忍度换系统效率，算法-系统 co-design 的活例）。
  5. Agentic RL 的新负载一句话预告：rollout 里嵌工具调用/环境交互 → 生成阶段变成「LLM+外部世界」的复合系统（接 L70）。
  6. 框架地形图（认名+一句话定位）：**veRL**（HybridFlow：single-controller 编排+hybrid engine）、OpenRLHF（Ray+vLLM 组合）、NeMo-RL 等；「读 RL infra 论文先认出它属于哪个架构象限」。
- **必收术语**：RLHF system、rollout、generation/experience 阶段、actor/critic/reward/reference（系统语义回收）、hybrid engine、colocated/disaggregated architecture、weight sync/update、resharding、rollout straggler/long-tail、partial rollout、async RL、off-policy（系统语境）、replay buffer（提名）、single controller（认名）、veRL/HybridFlow（认名）、OpenRLHF（认名）。
- **定量环节**：一步 GRPO 的时间预算示例：batch 512 prompts×8 samples、平均生成 4K token → rollout ≈（用 L55 的 decode 吞吐口径）数分钟级 vs 训练一步数十秒级 → **rollout 占 70–90% 时间**——「RL 系统优化 ≈ 推理系统优化」的量化依据；再算 weight sync：140 GB 广播到 128 台推理机在 400G 网络的时间与摊销比例。
- **图示**：① 四模型数据流图（回收 L15 图加系统标注）；② colocated vs disaggregated 双架构对比图（本课主图）；③ rollout 长尾甘特图（同步 vs async）。

- **误区**：「RLHF 只是加个 loss」——是两套分布式系统的联姻，系统难度远超 SFT；「rollout 用训练引擎顺便做就行」——生成态没有 KV cache/CB 的话慢一个量级；「async RL 免费加速」——off-policy 偏差是算法代价，需要联合评估（这正是 co-design 研究的空间）。
